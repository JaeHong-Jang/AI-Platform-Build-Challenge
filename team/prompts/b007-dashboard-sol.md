# 과제 B007 · 분석 (당신: sol, 실무팀) — 문제를 정확히 해결하는 대시보드 정보 구조
먼저 읽어라: `decisions/D003-이사-지킴이-제작계획.md`, `decisions/D004-이사-지킴이-웹-구현.md`, `wiki/overviews/이사-지킴이-웹-설계.md`, `wiki/sources/kca2026-소규모이사-피해.md`, `runs/out/b006-agent.sol.md`, 그리고 현재 코드 `web/src/lib/rules.ts`, `web/src/lib/agent.ts`, `web/src/lib/types.ts`.

사용자 피드백: 지금의 모바일 단계형(5단계 wizard) 화면은 안 된다. **대시보드 형태**여야 하고, AI 에이전트는 **로컬 Ollama**(텍스트 전용 qwen2.5:7b / qwen3:4b 등, 이미지 모델 없음)로 하며, **문제를 정확하게 해결**할 수 있어야 한다.

할 일:
1. **사용자가 대시보드를 여는 순간 한눈에 알아야 하는 것** — 계약금을 보내기 전 소비자의 결정(보낼까/더 물을까)에 필요한 정보를 우선순위대로. 예: 계약 위험 요약(확인 안 된 항목 수·금액에 영향 줄 수 있는 항목), 짐 대조표, 작업 조건, 추가비 조항, 업체 문의 상태(보냄/답 옴/미답), 근거.
2. **화면 구역 설계**: 대시보드의 패널 구성(상단 요약 KPI, 좌측 사건/견적 목록?, 중앙 대조표, 우측 에이전트 패널 등)을 구역별로 — 각 구역의 목적·들어갈 데이터(현재 types.ts 필드 기준)·사용자 행동. 견적을 여러 개 비교하는 경우(업체 A·B)도 다룰지 판단.
3. **에이전트가 문제를 '정확히' 해결하는 역할**: 텍스트 전용 로컬 모델 기준으로, 에이전트가 맡을 일과 규칙이 맡을 일을 다시 나눠라. 정확도를 높이는 장치(원문 대조, 상태 전이 제한, 사람 승인, 근거 없는 상태 변경 금지)를 구체적으로. "정확하게 해결"의 성공 기준을 측정 가능하게(예: 미답 항목을 '확인됨'으로 잘못 바꾸는 비율 0).
4. **이미지 입력이 없는 경우의 입력 경로**: 견적서를 텍스트(문자·카톡 복사, PDF 텍스트)로 받는 것이 오히려 실제 사용 순간에 맞는지 — 소규모 이사 견적이 실제로 어떤 형태(문자·카톡·앱 화면·종이)로 오는지 근거가 있으면 URL과 함께, 없으면 unknown.
5. 심사(서울시·관악구·청년 기관·서울대)에게 대시보드가 문제 해결을 증명하는 장면 1개(30초).
