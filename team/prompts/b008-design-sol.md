# 과제 B008 · 분석 — 이사 지킴이 v0.3 설계 명세 (독립 분석: 다른 팀원도 같은 질문을 따로 푼다)
먼저 읽어라: `briefs/B008-이사-지킴이-에이전트-관제.md`(사용자 요구 원문과 진행 기록), `runs/out/b008-triton.sonnet.md`(TRITON 화면·코드 구조 — 따라 할 디자인), `runs/out/b008-data.sol.md`(근거 자료: 쓸 수 있는 것/없는 것), `runs/out/b008-palette.sonnet.md`의 **A안**(사용자가 선택: 크라프트 상자 갈색 + 트럭 파랑), `decisions/D005-이사-지킴이-대시보드.md`(현재 v0.2), 현재 코드 `web/src/lib/{types,rules,agent,verify,store}.ts`, `web/src/components/*.tsx`.

사용자 요구(요약): ① 조건을 입력하면 그 조건으로 홈 화면이 만들어진다 ② 실제 사람이 이사하는 모습 UI — 에이전트가 이삿짐을 출발 집→트럭→도착 집으로 옮기는 장면을 보여 주면서 서류·문서 산정 결과가 쌓인다 ③ 앱 안 에이전트 팀: 오케스트레이터 1 + 3팀×3명, 왼쪽 레일에서 에이전트 활성/비활성 ④ 온톨로지 기반 근거 그래프 ⑤ AI 기능을 더 늘린다 ⑥ 선택(입력) 부담을 매우 완화 ⑦ 업체를 처음부터 정해 두지 않고, 어떤 업체를 쓰면 좋을지 고르는 기능 ⑧ TRITON 디자인 참고.

제약: 로컬 Ollama(Windows 호스트, 8GB GPU) — qwen3:4b-instruct(도구 호출 실측 성공, 웜 ~6초/턴), ax4-light 7B(구조화 JSON 읽기, 7~13초), 이미지 모델 없음. 두 모델을 번갈아 쓰면 다시 올리는 비용(콜드 37~112초). **근거 없는 숫자(짐 ㎥·톤수·인원·가격·업체 평점) 생성 금지** — b008-data의 unknown 항목은 앱이 숫자로 산정하면 안 된다. 실제 업체 이름을 지어내지 않는다. 해커톤(11/27, 하루)에서 시연, 예선 기획서(10/25)에 들어갈 설계.

산출물(마크다운 한 문서):
1. **사용자 흐름**: 첫 진입 → 조건 입력(최소 입력: 몇 번의 클릭/한 줄 문장) → 맞춤 홈 생성 → 이삿짐 장면 + 산정 → 견적 받기·여러 업체 비교 → 업체 고르기 → 계약 서류 점검 → 이삿날/사고 대응. 각 단계에서 사용자가 하는 행동과 기본값. 선택 부담을 줄이는 장치를 구체적으로(기본값, 자연어 한 줄 입력, '모름' 허용, 나중에 고치기).
2. **에이전트 조직표 (1 + 3×3)**: 팀 이름·각 에이전트 이름(한국어 역할명)·하는 일·LLM인지 규칙(결정적 코드)인지·입력/출력·도구·실행 순서와 병렬 여부·꺼졌을 때 무엇이 빠지고 어떤 화면에 '꺼짐' 표시가 되는지·사람 승인이 필요한 지점. LLM 호출은 로컬 GPU 한 대 기준 직렬이므로 전체 시간 예산(초)을 계산. 각 에이전트가 근거 없는 숫자를 만들지 않도록 막는 장치.
3. **AI 기능 목록**: 지금(v0.2: 견적 읽기, 답변 점검 에이전트) 대비 늘릴 기능. 각 기능의 근거 자료(b008-data의 어느 항목)와 정확도 장치. 근거 없는 기능은 넣지 말고 왜 뺐는지.
4. **근거 온톨로지**: 클래스(예: 짐, 작업조건, 견적문구, 서류항목, 약관조항, 업체, 증빙, 업체답변, 확인질문)와 관계, 상태(확인됨/미확인/모호/판독불가), TRITON `ontology.yaml`·`evidenceLayout` 방식과 대응. 그래프 화면에서 사용자가 보는 것(선택 부담을 늘리지 않게).
5. **화면 명세**: 레일 메뉴(에이전트 토글 포함), 각 화면의 패널 구성과 TRITON의 어떤 화면/코드를 본뜨는지(파일 경로), 이삿짐 장면(SVG — 무엇이 움직이고 무엇과 동기화되는지, 동작 줄이기 대응), 모바일 처리.
6. **구현 순서와 규모**: 해커톤 전까지 단계별(무엇을 먼저), 대략 파일·줄 수, 위험.
7. **성공 기준(측정 가능)**과 3분 시연 시나리오.
