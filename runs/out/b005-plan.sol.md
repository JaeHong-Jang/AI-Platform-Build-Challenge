# B005 제작 계획서 — 이삿날 “이건 추가요” 없게

**제안: 모바일 웹으로 ‘짐 사진 + 이미 받은 견적서 → 확인할 항목 → 업체에 보낼 합의 문구 → 당일 근거 카드’까지 구현한다.** 자동 부피·톤수 산정, 이사업체 매칭, 임대차 흠집 판정은 본선 범위에서 제외한다.

두 조사 파일을 모두 읽고 추가 조사했다. 특히 **Agoyu 공식 FAQ에서 상한 견적과 소비자 분쟁 지원을 확인했으므로, ‘소비자 보호’ 자체를 독점적 차별점으로 주장하면 안 된다.** 차별점은 **국내의 외부 견적서를 가져와 실제 짐·현장조건과 대조하는 사용 흐름**으로 좁힌다. [Agoyu FAQ](https://agoyu.com/faqs/)

이 문서는 **실무 분석안이며 peer/review 전**이다. 아래 구현 범위·일정·목표 수치는 제안이고, 효과 예상은 “추정:”으로 표시했다.

## 1. 한 줄 정의와 차별점

> **내가 받은 이사 견적서를 내 짐 사진·작업조건과 대조해, 추가요금으로 이어질 수 있는 미확인 사항을 찾아 업체에 보낼 확인 문구로 바꾸는 소비자용 도구.**

| 기존 서비스에서 확인한 범위 | 우리가 구현할 범위 | 주장 한계 |
|---|---|---|
| **Yembo:** 영상 조사로 물품 목록을 만들고 견적·고객 확인·사진 증빙으로 연결한다. [공식 소개](https://yembo.ai/moving/surveys) | 소비자가 다른 곳에서 받은 견적서와 자신의 짐 목록을 대조한다. | Yembo에 외부 견적서 대조 기능이 없는지는 **unknown**. |
| **Agoyu:** AI 짐 조사, 항목별 견적, 상한 견적, 변경사항 기록과 분쟁 지원을 설명한다. [공식 FAQ](https://agoyu.com/faqs/) | 한국 이사계약의 작업조건과 표준약관을 참고해 확인 질문을 만든다. | “추가요금 예방을 처음 한다”는 주장 금지. |
| **짐싸:** 여러 파트너의 견적을 받아 비교하는 흐름을 제공한다. [공식 앱 설명](https://apps.apple.com/kr/app/id1203174270) | 업체 선택 후, 계약 직전 문서의 구체성을 점검한다. | 앱 설명에서 확인되지 않은 기능을 ‘없음’으로 처리하지 않는다. |
| **미소:** 선행 조사에서 방문 영상·표준 견적·분쟁 증빙이 보도로 확인됐다. [보도](https://magazine.hankyung.com/job-joy/article/202511132159d) | 소비자가 직접 자료를 넣고 확인 요청을 작성한다. | 미소의 현행 AI 대조 기능은 **unknown**. |

**추정:** 여러 플랫폼·전화·문자로 견적을 받은 소비자가 업체를 다시 고르지 않고 사용할 수 있다는 점이 도입 동기가 될 수 있다. 실제 이용 의사와 지불 의사는 아직 **unknown**이다.

기획서 표현은 “국내 최초” 대신 다음이 적절하다.

> “조사한 공개 자료에서는 확인되지 않은 ‘외부 견적서와 실제 짐·작업조건의 대조’ 흐름에 집중합니다.”

## 2. 사용자와 사용 순간

**주 사용자 제안:** 원룸·소형 주거지 이사를 준비하며, 방문견적 없이 사진·전화·문자로 견적을 받은 청년 소비자.

한국소비자원의 2025년 소규모 이사 피해구제 분석 대상은 241건이며, 신청자의 65.1%가 20~30대였다. 추가비용 요구는 피해 유형별 집계에서 70건·24.9%였다. **전체 이사 이용자의 피해율이나 1인가구만의 통계는 아니다.** [한국소비자원](https://www.kca.go.kr/home/sub.do?menukey=4005&mode=view&no=1004458186&page=1)

| 시점 | 사용 목적 | 우선순위 |
|---|---|---|
| 견적 받을 때 | 짐 목록과 출발·도착지 작업조건 정리 | 보조 |
| **계약 직전** | 받은 견적에서 포함 여부·수량·추가비 조건 확인 | **핵심** |
| 이사 당일 | 합의한 품목·작업조건·답변을 즉시 확인 | 핵심의 연장 |
| 입주 후 | 필요한 기록 내려받기·삭제 | 최소 제공 |

**추정:** 가장 설득력 있는 진입 문구는 “견적 받기”보다 **“계약금 보내기 전에 확인하기”**다.

## 3. 핵심 기능 — P0/P1/P2

P0는 **1인 참가에서도 완주할 최소 범위**, P1은 P0 안정화 후 추가, P2는 후속 개발이다.

| 우선순위·기능 | 입력 → 처리 → 출력 |
|---|---|
| **P0 짐 목록 초안** | 방 사진 3~5장 → VLM이 보이는 큰 가구·가전의 후보와 사진 번호 추출 → 사용자가 품목·수량·가져갈지 수정 |
| **P0 견적 항목 추출** | 견적서·계약서 사진 1~2장 → OCR 및 구조화 → 총액, 차량, 인력, 품목, 포장, 장비, 추가비 문구와 원문 위치 |
| **P0 현장조건 질문** | 출발·도착지 층수, 엘리베이터, 사다리차, 주차·운반거리, 분해·설치 필요 여부 → 미응답 확인 → 견적과 대조할 조건표 |
| **P0 대조 카드** | 사용자 확인 목록 + 견적 항목 → 규칙 비교 → ‘명시됨 / 포함 여부 미확인 / 조건 모호 / 판독 불가’ |
| **P0 확인 문구** | 선택한 카드 → 검토한 문장 틀에 실제 항목 삽입 → 업체에 복사해 보낼 질문 |
| **P0 당일 근거 카드** | 확인한 목록·견적 발췌·사용자가 첨부한 업체 답변 → 한 화면으로 묶기 → 화면 저장 및 텍스트 내려받기 |
| **P1 답변 재점검** | 업체 답변 캡처 → 답한 항목과 여전히 미확인인 항목 추출 → 사용자가 확인 상태 변경 |
| **P1 공유 링크** | 사용자가 선택한 최소 자료 → 만료·폐기 가능한 읽기 링크 → 업체 열람 |
| **P1 영상 보조** | 짧은 영상 → 장면을 정지사진으로 선택 → 기존 사진 분석 경로 사용 |
| **P2** | 다중 견적 비교, 전자서명 연동, 변경 합의 이력, 전문 상담 연계 |

**대조의 중요한 원칙:** 견적에 “가구 일체”라고 적혀 있으면 책장을 ‘누락’으로 단정하지 않는다. **“책장 1개가 포함되는지 문서만으로 확인하기 어려움”**으로 표시한다.

**가상 시연용 확인 문구:**

> “첨부 목록의 책장 1개를 포함한 운송과 출발지 3층 계단 작업이 총액 35만 원에 포함되는지 확인 부탁드립니다. 별도 비용이 있다면 항목·발생조건·금액 또는 산정방식을 계약 전에 적어 주세요. 변경 작업이 생기면 작업 전에 사유와 추가금액을 안내하고 확인받는 방식으로 진행하고 싶습니다.”

이는 **합의를 요청하는 초안**이다. 전송만으로 계약이 변경되거나 추가금이 차단되지는 않는다.

**입주·퇴거 흠집 기록은 P2로 분리한다.** 추정: 임대인과의 보증금 분쟁까지 포함하면 계약 상대방·판정 기준·촬영 흐름이 달라져 핵심 시연이 흐려진다. 이사 물품의 사전 상태 사진은 기존 근거 카드에 첨부할 수 있게 하되 자동 파손 판정은 하지 않는다.

## 4. AI·규칙·사람의 역할

| 작업 | AI | 규칙 | 사람 |
|---|---|---|---|
| 짐 파악 | 사진 속 품목 후보·사진 번호 제안 | 허용된 품목 구조 검사 | 실제 물건, 수량, 중복, 운송 대상 확인 |
| 문서 읽기 | OCR 결과에서 계약 항목 구조화 | 금액·단위·필수 필드 검사 | 원문과 금액·제외조건 대조 |
| 품목 대응 | ‘책꽂이↔책장’ 등 대응 후보 제안 | 확인된 대응관계로 비교 | 애매한 품목 연결 확정 |
| 미확인 사항 찾기 | 관련 문구·조건 후보 추출 | 명시 여부·미응답·조건 부족 판단 | 실제 계약 범위 확인 |
| 확인 문구 | 선택적으로 자연스럽게 다듬기 | 승인된 문장 틀·출처만 사용 | 수정·전송·업체 답변 확인 |
| 당일 대응 | 자료 찾기 보조 | 관련 카드·기준 표시 | 협의·상담 여부 결정 |
| 적법성·배상 판단 | 자동 확정하지 않음 | 참고 기준 제공 | 필요시 전문기관에 확인 |

**설계 원칙:** AI가 출력한 신뢰도 숫자를 정확도 보증으로 보여주지 않는다. 사용자 확인 전에는 분석 완료가 아니라 **‘초안 확인 중’**이다.

## 5. 웹 vs 앱 결정

**결론: 설치 없이 쓰는 모바일 웹을 선택한다. PWA 설치·오프라인 기능은 P1이다.**

| 기준 | 모바일 웹/PWA | 네이티브 앱 | React Native·Flutter |
|---|---|---|---|
| 촬영·업로드 | 사진 파일 입력으로 시작 가능 | 전용 촬영 흐름 설계 가능 | 카메라 모듈·권한 연동 필요 |
| 현장 사용 | 저장한 카드로 보완 | 로컬 저장 중심 설계 가능 | 로컬 저장 중심 설계 가능 |
| 업체 공유 | URL·복사 문구로 연결 | 별도 웹 열람 경로 설계 필요 | 별도 웹 열람 경로 설계 필요 |
| 설치 흐름 | 브라우저 접속으로 시작 | 앱 설치 필요 | 앱 배포 시 설치 필요 |
| 팀 적합성 | 웹 강점과 일치 | 별도 플랫폼 작업 발생 | 웹 경험 일부 활용 가능하나 별도 검증 필요 |
| 9시간 구현 | **추정: 가장 유리** | 추정: 배포·기기 대응 부담 큼 | 추정: 모듈·빌드 검증 부담 큼 |
| 심사 시연 | QR 접속 + PC 화면 동시 설명 | 설치된 단말 중심 | 설치된 단말 중심 |

**브라우저 근거와 구현 방식**

- 사진은 `<input type="file" accept="image/*" capture="environment">`를 후보로 사용한다. `capture`는 촬영 장치 선택을 요청하는 속성이며, 실제 UI는 환경에 따라 달라진다. **촬영 버튼과 앨범 업로드 버튼을 별도로 제공**한다. [MDN HTML capture](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/capture)
- WebKit은 iOS 11 Safari의 WebRTC·미디어 캡처 지원을 공식 발표했다. 직접 카메라 미리보기를 구현할 때 사용하는 `getUserMedia()`에는 보안 컨텍스트와 사용자 권한 조건이 있다. [WebKit](https://webkit.org/blog/7726/announcing-webrtc-and-media-capture/), [MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)
- WebKit은 iOS 14.3 베타에서 `MediaRecorder` 기본 활성화를 발표했다. 다만 영상 코덱은 기능 탐지가 필요하므로 **영상 촬영을 P0 성공 조건에 넣지 않는다.** [WebKit MediaRecorder](https://webkit.org/blog/11353/mediarecorder-api/)

**실기기 검증 조건:** iPhone Safari와 Android Chrome에서 촬영·앨범 업로드·권한 거절·재업로드·화면 저장을 확인한다. 카카오톡 등 인앱 브라우저의 실제 동작은 **unknown**이므로 Safari/Chrome 열기 안내를 제공한다.

## 6. 기술 구조

### 선택안

| 계층 | 선택 제안 | 이유·대안 |
|---|---|---|
| 프런트 | React + TypeScript, 팀이 익숙하면 Next.js | 추정: 화면과 서버 API를 한 프로젝트로 관리하기 유리 |
| 백엔드 | 서버 API에서 AI 호출·검증 | API 키를 단말에 두지 않고 입력 크기·응답 구조 통제 |
| VLM·LLM | **GPT-5.4 mini 후보**, 준비기간 실측 후 고정 | 공식 문서상 이미지 입력·텍스트 출력·Structured Outputs 지원. 본 과제 정확도와 지연은 unknown. [공식 문서](https://developers.openai.com/api/docs/models/gpt-5.4-mini) |
| OCR | 기본안은 동일 VLM으로 최소 구성, **CLOVA General OCR을 비교 후보**로 평가 | CLOVA는 글자·위치·인식 신뢰도를 반환한다. 숫자·원문 근거 표시가 더 안정적이면 채택. [General OCR API](https://api.ncloud-docs.com/docs/ai-application-service-ocr-ocr) |
| 규칙 | 버전 있는 JSON + TypeScript 함수 | 허용한 규칙만 실행하고 조항을 임의 생성하지 않음 |
| 저장소 | P0 서버 영구 저장 없이 처리, 내려받기는 단말 중심 | 공유 링크를 제외해 저장·접근제어 범위 축소 |
| P1 저장소 | 비공개 객체 저장소 + 메타데이터 DB | 만료·삭제·접근권한을 구현할 때 도입 |
| 물체 탐지 대안 | Grounding DINO 계열 | 위치 표시 연구 후보. 모델 배포·연동을 늘리므로 당일 핵심 경로에서는 제외 |

AI API 선택은 **OpenAI Docs와 공식 OCR 문서로 지원 기능을 확인한 후보안**이다. 계정 사용 가능 여부, 최종 비용, 한국어 견적 정확도는 실제 호출 전까지 **unknown**이다.

### 데이터 흐름

```text
방 사진 ─────────→ VLM ──────→ 짐 목록 초안 ──→ 사용자 수정·확인
                                                       │
견적 사진 → OCR/VLM → 원문 연결 계약 항목 → 사용자 확인 │
                                                       ▼
현장조건 질문 ───────────────────────────────→ 규칙 대조
                                                       │
                     미확인 사항 + 사진/문서 근거 + 참고 조항
                                                       │
                           검토된 문장 틀 → 확인 요청 복사
                                                       │
                  사용자가 업체에 전송 → 업체 답변 첨부·확인
                                                       │
                               당일 카드 → 단말 저장·내려받기
```

규칙 입력에는 `품목`, `수량`, `사진 ID`, `원문 발췌`, `문서 페이지`, `포함 상태`, `사용자 확인 상태`를 둔다. 모르는 값은 빈칸을 임의 보충하지 않고 `unknown`으로 유지한다.

### 집 내부 사진 처리 원칙

1. **본선은 팀이 촬영 권한을 가진 사진과 가상 견적서만 사용**한다.
2. 업로드 전에 얼굴·문서·주소·가족사진을 확인하고 가릴 수 있게 한다. 가리지 못한 이미지는 사용자가 전송을 취소할 수 있다.
3. 변환 이미지의 위치정보 등 메타데이터를 제거하고, 전송 대상 API와 처리 목적을 안내한다.
4. P0 서버에는 원본을 영구 저장하지 않는다. 사진·OCR 전문·주소를 로그에 남기지 않는다.
5. 자료 다운로드와 서비스 삭제를 구분한다. 단말에 저장한 파일은 사용자가 관리한다.
6. 실제 공개 서비스 전에는 외부 처리·국외 이전 해당 여부와 고지·계약 조건을 별도 확인한다.

**‘우리 서버 미저장’은 ‘외부 API 무보관’을 뜻하지 않는다.** OpenAI API 문서는 기본적으로 학습 이용 여부와 별개로 남용 모니터링 로그 보관을 설명한다. `store:false`만으로 모든 보관이 사라진다고 안내하면 안 된다. [OpenAI 데이터 통제](https://developers.openai.com/api/docs/guides/your-data)

## 7. 기술 근거와 한계

| 검토 대상 | 확인한 근거 | 이 과제에 적용할 결론 |
|---|---|---|
| 물체 식별 | **Grounding DINO**는 텍스트로 지정한 물체를 탐지하며 COCO zero-shot 전이 평가에서 **52.5 AP**를 보고했다. [논문, arXiv:2303.05499](https://arxiv.org/abs/2303.05499) | 일반 물체 탐지의 가능성 근거다. **한국 원룸 가구 인식률 52.5%라는 뜻이 아니다.** |

**현재 답할 수 없는 성능:** 선택 API가 한국 원룸의 가구·가전을 몇 % 인식하는지, 가려진 물건과 수납장 내부 물품을 얼마나 놓치는지, 견적 금액을 얼마나 정확히 읽는지는 모두 **unknown**이다. 자체 세트로 측정해야 한다.

**부피·톤수 우회 설계**

- 사진만으로 실제 치수를 확정하지 않는다.
- 큰 품목에는 ‘치수 확인 필요’, 분해 여부에는 ‘업체 확인 필요’를 붙인다.
- 사용자가 치수를 입력해도 계산값은 외접 직육면체의 참고 부피이며, 차량 배정 결과로 사용하지 않는다.
- 톤수·차량·인력은 **업체가 확인한 계약조건**을 기록한다.
- 흐릿한 문서, 금액 미판독, 페이지 누락은 재촬영 또는 수동입력으로 넘긴다.
- 견적에 적힌 총액과 세부합계가 맞지 않으면 원문을 보여주며 확인을 요청한다.

## 9. 평가 방법과 성공 지표

**아래 숫자는 실측 결과가 아닌 제안 목표다.**

### 평가 세트

- 권한 있는 방 사진 **10세트**, 세트당 3~5장.
- 방별로 정상 견적·누락 견적·모호 견적을 만들어 **가상 견적 30건** 구성.
- 정상 견적에도 포함·제외조건을 명확히 넣어 오탐을 측정.
- 가림, 중복사진, 가져가지 않는 물건, 계단 작업, 분해·조립, 금액 오독 사례 포함.
- 방 단위로 개발용 4세트와 최종 평가용 6세트를 분리한다. 최종 평가는 **18건**이며, 같은 방을 양쪽에 나누지 않는다.
- 정답은 품목·수량·문서 필드·미확인 사항·근거 위치로 기록한다. 2인 이상이면 다른 사람이 검토하고, 1인이면 독립 검증 부재를 명시한다.

| 지표 | 측정법 | 목표 제안 |
|---|---|---|
| 짐 인식 | 사용자 수정 전, 보이는 운송 대상 품목의 precision·recall | 각각 85% 이상 |
| 핵심 문서 추출 | 총액·차량·인력·추가비 문구의 정확 일치 | 필드 정확도 95% 이상 |
| 미확인 사항 탐지 | TP/(TP+FN), TP/(TP+FP) | recall 90%, precision 85% 이상 |
| 정상 견적 오탐 | 정상 견적당 잘못 표시한 카드 수 | 평균 1개 이하 |
| 근거 연결 | 카드와 실제 사진·문서 발췌의 일치 | 95% 이상 |
| 처리 시간 | 업로드 완료부터 첫 결과까지 | 중앙값 30초, p95 60초 이하 |
| 사용자 완료 | 처음 보는 사용자 5명이 수정·문구 복사 완료 | 4명 이상, 3분 이내 |
| 금지 출력 | ‘무조건 불법’, 없는 조항·확인되지 않은 합의 생성 | 평가 세트에서 0건 |

**AI 단독 결과와 사용자 수정 후 결과를 분리**해서 보고한다. 실패·시간초과도 전체 분모에 포함하고, 소표본이라는 한계를 밝힌다.

**추정:** 이 단계에서 입증할 효과는 실제 추가요금 감소보다 **‘계약 전에 확인할 항목을 더 잘 찾는가’**다. 실제 분쟁 감소율은 후속 실사용 연구 전까지 **unknown**이다.

## 13. 기획서 문장 초안

### ① 문제와 주요 사용자

한국소비자원의 2025년 소규모 이사 피해구제 분석에서 추가비용 요구는 피해 유형별 집계의 24.9%를 차지했습니다. 이는 전체 이용자의 피해율은 아니지만, 계약 전 확인이 필요한 문제를 보여줍니다. [한국소비자원](https://www.kca.go.kr/home/sub.do?menukey=4005&mode=view&no=1004458186&page=1)  
저희는 사진·전화·문자로 견적을 받은 뒤 계약금을 보내려는 청년 소비자를 주요 사용자로 설정했습니다. 추정: 소비자가 짐과 현장조건의 포함 범위를 쉽게 확인한다면 당일의 해석 차이를 줄이는 데 도움이 될 수 있습니다.

### ② 핵심 기능과 이용 흐름

사용자가 방 사진과 받은 견적서를 올리면 AI가 짐 목록과 견적 항목의 초안을 만듭니다. 사용자가 수량·운송 대상·작업조건을 확인하면 서비스는 문서에 명시되지 않았거나 모호한 항목을 근거와 함께 보여줍니다. 사용자는 필요한 항목을 골라 업체에 보낼 확인 문구를 복사하고, 받은 답변을 기록합니다. 이사 당일에는 사진·견적·답변을 묶은 카드로 합의 내용을 확인합니다.

### ③ AI 적용 방식·데이터·기술 구성

이미지 입력 API와 OCR로 품목·문서 항목을 추출하고, 검토한 규칙으로 포함 여부와 작업조건의 명시 상태를 대조합니다. 이미지 이해 모델에는 개수·공간·한국어 작은 글씨 인식의 한계가 있으므로 사용자 확인을 필수 단계로 둡니다. [OpenAI 공식 문서](https://developers.openai.com/api/docs/guides/images-vision)  
모델 학습 없이 권한 있는 자체 사진·가상 견적서·공개 기준의 검토된 요약을 사용합니다. 모바일 웹으로 구현하며, 사진만으로 부피·차량 톤수나 추가요금의 적법성을 확정하지 않습니다.

### ④ 구현 계획·역할 분담·기대 효과

준비기간에는 사용자 조사, API 성능 실험, 조항 검증과 평가 세트를 마련하고, 본선 당일에는 업로드부터 확인 문구·당일 카드까지 연결합니다. 팀원은 프런트, AI·백엔드, 규칙·검증 역할을 인원에 맞춰 나눕니다. 자체 평가에서는 미확인 사항 탐지율·오탐·문서 추출 정확도·처리 시간·사용자 완료 시간을 측정합니다. 추정: 계약 전 확인할 항목을 구체화하고 합의 기록을 찾는 부담을 줄일 수 있으며, 실제 추가요금 감소 효과는 후속 실사용 평가로 확인하겠습니다.
