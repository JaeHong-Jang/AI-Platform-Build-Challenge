# B007 분석 — 계약금 송금 전 확인을 끝내는 대시보드

**제안: 대시보드의 중심을 ‘내 짐·작업조건과 업체가 적어 준 내용의 대조표’로 둔다.** 사용자는 화면을 열자마자 **무엇이 아직 확인되지 않았고, 누구에게 무엇을 물어야 하는지** 알아야 한다. 로컬 Ollama 에이전트는 견적·답변에서 근거를 찾아 연결하고, 규칙과 사용자 승인이 상태 변경을 통제한다.

이 문서는 Sol의 분석 제안이다. D003·D004의 기존 결정과 달라지는 범위를 표시했으며, 채택 전 peer 또는 review가 필요하다. 파일 수정과 모델 실측은 하지 않았다. 아래 설계·검증 목표는 제안이며 달성 여부는 **unknown**이다.

**1. 사용자가 첫 화면에서 알아야 하는 것**

한국소비자원은 소규모 이사에서 구두 설명·온라인 입력에 기초한 비대면 계약이 많고, 당일 짐의 양이나 건물 구조를 이유로 차량·인력·사다리차 추가 비용을 요구하는 피해가 발생한다고 설명한다. 대시보드는 이 조건들이 견적에 구체적으로 반영됐는지 확인하도록 설계한다. [한국소비자원 피해예방주의보](https://www.kca.go.kr/home/sub.do?menukey=4005&mode=view&no=1004458186&page=1)

| 우선순위 | 사용자의 질문 | 첫 화면에 보여 줄 정보 | 다음 행동 |
|---|---|---|---|
| 1 | 계약금 보내기 전에 더 물을 게 있나? | **계약 전 확인 남음 N항목**, 핵심 항목 이름 | 남은 항목 펼치기 |
| 2 | 어떤 부분이 금액을 바꿀 수 있나? | 계단·사다리차·운반 거리·추가비 중 **조건 또는 금액 미확인 항목** | 해당 조건을 업체에 묻기 |
| 3 | 지금 받은 금액은 무엇인가? | 업체명·이사일·총액·계약금, 각 값의 출처와 확인 여부 | 금액 원문 확인·수정 |
| 4 | 내 짐이 실제 견적에 반영됐나? | 운송할 품목·수량과 견적·답변의 대응 상태 | 누락·수량 차이 확인 |
| 5 | 이미 물었고 답을 받은 항목은 무엇인가? | 문의 전 / 보냈다고 기록 / 미답 / 답변 검토 대기 / 반영 | 답변 붙여넣기·후속 문의 |
| 6 | 왜 이런 결과가 나왔나? | 선택한 행의 원문 발췌·문서 위치·판정 이유 | 원문 대조 |

첫 문장은 상태에 따라 다음처럼 만든다.

- **“계약금 보내기 전 3항목을 더 확인하세요: 계단 비용, 박스 수량, 추가비 조건.”**
- 입력이 부족하면 **“판단에 필요한 입력이 남았습니다: 짐 목록, 도착지 층수.”**
- 점검 항목이 모두 해소되면 **“현재 입력과 점검 범위에서 미확인 항목이 없습니다.”**

`미확인 0`을 `송금 안전`으로 바꾸지 않는다. 입력하지 않은 짐이나 조건까지 확인한 것은 아니므로, 요약 옆에 **“사용자가 확인한 짐 N종·작업조건 기준”**을 표시한다.

현재 네 가지 `CardStatus`는 유지하되 설명을 고정한다.

| 상태 | 화면에서 설명할 의미 |
|---|---|
| 명시됨 | 해당 사실·조건이 원문에 구체적으로 적혀 있음. 비용 포함 여부는 별도로 확인 |
| 포함 여부 미확인 | 해당 항목의 포함 여부를 확인할 근거가 없음 |
| 조건 모호 | 포괄 표현, 조건부 답변, 상충하거나 불완전한 조건이 있음 |
| 판독 불가 | 입력 자료에서 값을 읽거나 추출하지 못함 |

**중요한 보완:** `명시됨` 하나로 ‘품목 이름이 적힘’, ‘총액에 포함됨’, ‘별도 비용이 구체적으로 적힘’을 함께 표현하면 오해가 생긴다. 대조표에는 **기재 상태와 비용 처리**를 나란히 표시해야 한다. 예를 들어 `사다리차 별도 10만 원`은 구체적 기재일 수 있지만 총액 포함은 아니다.

확률 근거가 없는 위험 점수, 예상 추가비, 절감액은 표시하지 않는다.

**2. 화면 구역과 현재 타입의 연결**

추정: 데스크톱은 **상단 요약 + 좁은 좌측 탐색 + 넓은 중앙 대조표 + 우측 답변 점검 패널**이 적합하다. 모바일에서는 같은 내용을 세로로 배치하고 요약·남은 항목 이동을 유지한다. 입력을 끝내야 결과를 볼 수 있는 5단계 흐름은 없앤다.

```text
┌──────────────────────────────────────────────────────────┐
│ 업체·이사일 | 총액·계약금 | 확인 남음 | 비용 조건 미확인 │
├──────────┬──────────────────────────┬────────────────────┤
│ 현재 이사 │ 짐·작업조건·추가비 대조표 │ 문의·답변 점검      │
│ 자료 목록 │                          │ 원문 붙여넣기       │
│ 구역 이동 │ 내 입력 ↔ 업체 원문       │ 갱신 후보 검토      │
│          ├──────────────────────────┤ 남은 질문 복사      │
│          │ 선택한 행의 원문·근거     │                    │
└──────────┴──────────────────────────┴────────────────────┘
```

| 구역 | 목적 | 현재 필드로 표시할 데이터 | 사용자 행동·보완점 |
|---|---|---|---|
| 상단 사건 정보 | 어느 견적을 보는지 고정 | `QuoteDraft.company`, `moveDate`, `totalAmount`, `deposit` | 원문 확인·값 수정. `null`은 0원이 아닌 `미기재/미확인` |
| 상단 요약 KPI | 남은 확인과 다음 행동 파악 | `Card.status`, `rule`, `answered`, `missingFacts(conditions)` | KPI 클릭 시 해당 행만 필터 |
| 좌측 현재 이사·자료 | 자료와 작업 맥락 유지 | 현재 단일 `QuoteDraft`, `Item[]`, `Conditions` | 견적 원문 교체·짐 목록 편집. 자료 ID·버전은 추가 필요 |
| 중앙 짐 대조표 | 내 짐과 업체 기재 비교 | `Item.name/category/count/move/uncertain`, `listedItems`, `blanketPhrases`, 품목 `Card` | 운송 여부·수량 수정, 행별 문의 선택 |
| 중앙 작업조건 | 출발·도착 조건별 공백 확인 | `Conditions.from/to.floor/elevator/parkingFar`, `ladderNeeded`; 견적 `truck/workers/stairsNote/ladder` | 현장 사실 입력·업체 비용 조건 확인 |
| 중앙 추가비 | 발생 조건·금액·포함 범위 확인 | `extraFeeClauses`, 추가비 `Card` | 항목·조건·금액 또는 산정 방식 문의 |
| 우측 문의·에이전트 | 질문부터 답변 반영까지 연결 | `Card.ask/answered`, `AgentRun.steps/proposals/stopped`, `Proposal` | 요청문 복사·발송 기록·답변 입력·후보별 승인 |
| 선택 행 근거 | 결과를 직접 검증 | `Card.why/evidence/refs`, 원문 발췌 | 원문 위치 강조·교정·갱신 이력 확인 |

중앙 대조표의 기본 열은 다음과 같다.

| 대상 | 내가 확인한 내용 | 견적·답변 원문 | 기재 상태 | 비용 처리 | 문의 상태 |
|---|---|---|---|---|---|
| 책장 | 1개 운송 | “책장 1개 포함” | 명시됨 | 총액 포함 | 답변 반영 |
| 출발지 계단 | 3층·엘리베이터 없음 | “현장 보고 결정” | 조건 모호 | 금액 미확인 | 재문의 필요 |
| 박스 | 10개 운송 | “원룸 짐 일체” | 조건 모호 | 수량 범위 미확인 | 미답 |

위 표는 **가상 예시**다.

**요약 수치는 승인된 현재 상태로 계산한다.** `AgentRun.open`은 현 구현에서 승인 전 제안까지 반영해 산출되므로, 이를 그대로 상단 미확인 수로 사용하면 안 된다. `확인 남음 3 · 반영 후보 1`처럼 분리한다.

**문의 상태는 별도 데이터가 필요하다.** 현재 `Card.answered`만으로는 요청문 작성·발송·미답·검토 대기를 구분할 수 없다.

| 문의 상태 | 전환 조건 |
|---|---|
| 문의 전 | 아직 발송 기록 없음 |
| 보냈다고 기록 | 사용자가 실제 발송했다고 표시 |
| 미답 | 해당 문의에 연결된 답변이 아직 없음 |
| 답변 검토 대기 | 답변을 입력했지만 근거 검토·승인이 끝나지 않음 |
| 답변 반영 | 검증된 후보를 사용자가 승인함 |
| 재문의 필요 | 조건부·상충·부분 답변으로 확인이 남음 |

복사 버튼 클릭은 발송으로 취급하지 않는다. 외부 메신저 연동이 없으므로 `답 옴`도 자동 감지한다고 표시하지 않는다.

**다중 견적은 이번 핵심 구현에서 제외할 것을 제안한다.** D003에서도 P2였고, 현재 타입은 단일 견적이다. 우선 한 업체의 견적→문의→부분 답변→후속 문의를 완결한다.

추후 A·B 비교를 추가한다면 동일한 짐·작업조건 아래 총액, 계약금, 비용 조건, 미확인 항목을 비교한다. 견적별 문서·답변·승인은 분리하고, 싼 금액만으로 추천하지 않는다. 조건이 다른 견적에는 `동일 조건 비교 아님`을 표시한다.

**3. 로컬 에이전트가 정확하게 맡을 일**

현재 `agent.ts`는 `provider.ts`의 Anthropic 호출 구조를 사용한다. 따라서 현재 코드가 이미 Ollama로 동작한다고 설명할 수 없다. 텍스트 전용 로컬 모델로 바꾸면서 제공자 어댑터·도구 응답 처리·오류 처리를 변경해야 한다. 지정 모델들의 한국어 대응 정확도와 실행 지연은 **unknown**이다.

| 담당 | 맡을 일 |
|---|---|
| 텍스트 모델 단순 추출 | 견적 텍스트에서 금액·인원·품목·비용 조항을 **원문 근거가 있는 초안**으로 추출 |
| 답변 점검 에이전트 | 현재 카드·견적·업체 답변을 조회하고, 항목별 답변 근거를 찾아 갱신 후보 제출 |
| 규칙 코드 | 입력 검증, 근거 위치 검사, 수량·금액 검증, 허용 상태 전이, KPI 계산, 질문 문장 틀 |
| 사용자 | 실제 짐·현장 조건 확인, 원문과 후보 대조, 상태 변경 승인, 외부 발송 |

에이전트의 목표는 **“각 문의 항목에 업체가 무엇을 답했고 무엇을 답하지 않았는지 근거와 함께 정리한다”**로 제한한다. 업체 추천·가격 적정성·법적 판단은 목표에 넣지 않는다.

**현재 코드에서 우선 보완할 정확도 문제**

| 코드상 확인한 동작 | 문제 | 보완 제안 |
|---|---|---|
| `itemCards()`가 정규화한 품목명이 일치하면 `명시됨` 처리 | 내 책장 2개와 견적 책장 1개도 구분하지 못함. `listedItems.quote`의 제외 문구도 판정에 쓰지 않음 | 품목 존재·수량·포함/제외를 분리해 비교 |
| `canonical()`이 크기 표현 등을 제거하고 동의어로 묶음 | 서로 다른 물품·규격의 자동 합치기 가능 | 원래 이름·규격 보존, 대응 후보를 사용자 확인 |
| `feeCards()`가 모든 추가비 문구를 `조건 모호`로 처리 | 조건·금액이 구체적인 문구도 해소되지 않음 | 발생 조건·금액/산식·포함 여부를 구조화 |
| 운반 거리 카드는 `parkingFar === "있음"`이면 미확인 생성 | 견적에 관련 조건이 있어도 반영할 필드가 없음 | 출발·도착별 운반 조건·근거 필드 추가 |
| 에이전트 검증이 원문 부분문자열·키워드·금지어 중심 | 항목 이름만 있는 불완전한 발췌가 통과할 수 있음. “추가 비용 없습니다”도 `추가` 때문에 거절될 수 있음 | 문장 전체·긍정/부정·대상·수량·조건을 검토 |
| `get_open_cards()`가 이미 `명시됨`인 항목 제외 | 새 답변이 기존 명시 내용을 뒤집는 경우를 놓칠 수 있음 | 열린 카드와 기존 확정 내용을 함께 조회 |
| UI에서 모든 갱신 후보를 기본 선택 | 일괄 반영을 유도 | 기본 미선택, 원문을 보며 개별 승인 |

금지어를 늘리는 것만으로 자연어 의미 검증이 완성되지는 않는다. **규칙이 검증하지 못한 문장은 후보·미확인 상태로 남기는 것**이 기본 동작이어야 한다.

**정확도를 높이는 구체적 장치**

1. **원문을 보존한다.** 견적·답변마다 `sourceId`, 원문, 버전과 문자 위치를 저장한다. 발췌는 모델이 재작성하지 않고 해당 범위에서 코드가 가져온다. 줄바꿈을 제거하기 전 문장을 보존한다.

2. **필드마다 근거를 붙인다.** 총액·계약금·인원·품목 수량도 근거 위치를 요구한다. `null`을 추정값으로 채우지 않는다. 사용자의 직접 입력은 업체 문서 근거와 구분한다.

3. **질문의 충족 조건을 고정한다.** 책장 문의라면 품목·수량·운송 및 총액 포함 여부, 계단 문의라면 출발/도착·층수·비용 처리가 대상이다. 이름이 등장했다는 이유만으로 질문 전체가 해소되지 않는다.

4. **포괄 답변을 확장하지 않는다.** “다 포함이에요”는 개별 품목의 근거로 자동 적용하지 않는다. “네”처럼 앞 질문과 연결해야 하는 답변은 질문·답변 묶음을 함께 보여 주고 사람이 대응을 확인한다.

5. **상충 답변을 덮어쓰지 않는다.** 기존 견적과 새 답변이 다르면 두 원문을 병렬 표시한다. 자동으로 최신 문장을 정답으로 채택하지 않는다.

6. **상태 변경은 원자적으로 검증한다.** `caseId`, `quoteId`, `cardId`, 원문 버전, 짐·조건 버전, 변경 전 상태가 모두 일치할 때만 승인한다. 입력이 바뀌면 관련 후보를 무효화한다.

7. **문의·에이전트 상태와 계약 확인 상태를 분리한다.** 답변 도착·모델 실행 완료·후보 생성은 확인 완료가 아니다. 무응답은 기존 상태를 유지한다.

8. **오류에서 상태를 보존한다.** 도구 횟수·턴·시간 상한을 두고, 형식 오류·모델 중단·시간 초과에서는 기존 상태를 유지한다. 사용자는 원문 옆에서 직접 확인을 이어갈 수 있어야 한다.

추가할 최소 데이터는 `SourceDocument`, 필드별 `EvidenceRef`, `Inquiry`, `ChangeLog`, 그리고 비용의 `포함/별도/미확인` 및 조건·금액/산식이다. 모두 **새 설계 제안**이며 현재 `types.ts`에 구현돼 있지 않다.

**측정 가능한 성공 기준**

다음 수치는 **제안 목표**이며 실측 결과가 아니다.

| 검증 항목 | 측정 방법 | 목표 |
|---|---|---|
| 미답·포괄 답변의 잘못된 확인 처리 | 정답상 미해결인 항목 중 해소 후보가 된 비율 | 고정 평가셋에서 0% |
| 조건부·제외·상충 답변의 잘못된 포함 처리 | 해당 사례 중 `총액 포함` 후보가 된 비율 | 고정 평가셋에서 0% |
| 근거 무결성 | 승인 후보의 출처·범위·원문 일치 검사 | 100% |
| 승인 전 상태 변경 | 후보 생성·취소·오류 전후 상태 비교 | 0건 |
| 오래된 후보 적용 | 원문·수량·조건 변경 후 이전 후보 승인 시도 | 수락 0건 |
| 명시적인 답변을 제대로 찾기 | 정답상 명시 답변 중 올바른 후보를 낸 비율 | 90% 이상 |
| 장애 시 상태 보존 | 잘못된 JSON·시간 초과·모델 중단 주입 | 오변경 0건 |
| 실제 사용자 판단 | 첫 화면에서 남은 항목과 다음 행동 설명 | 5명 중 4명이 10초 내 설명 |

평가셋은 **합성 사례 최소 40개**로 구성할 것을 제안한다. 명시·부분 답변, 무응답, 포괄 표현, 부정, 조건부, 상충, 수량 차이, 출발/도착 혼동, 다른 업체 답변, 원문 속 지시문을 포함한다.

후보 단계 오류와 사용자 승인 후 오류를 별도로 측정한다. 전부 미확인으로 남겨 오류율만 낮추는 것을 막기 위해 명시 답변 재현율도 함께 본다. 평가셋의 오류 0건을 실제 모든 입력에서의 오류율 0%라고 주장하지 않는다.

**4. 이미지 없이 입력받는 경로와 근거의 한계**

**확인된 사실:** 소비자원 자료는 구두 설명·온라인 홈페이지 입력에 기초한 비대면 계약이 많다고 설명한다. **소비자가 최종 견적을 어떤 매체로 받는지의 분포는 확인하지 못했다.** [한국소비자원 원문](https://www.kca.go.kr/home/sub.do?menukey=4005&mode=view&no=1004458186&page=1)

| 견적 전달 형태 | 현재 확인 수준 |
|---|---|
| 문자메시지 | 실제 사용 빈도·비중 **unknown** |
| 카카오톡 | 실제 사용 빈도·비중 **unknown** |
| 앱 내 견적 화면 | 실제 사용 빈도·복사 가능 여부 **unknown** |
| 텍스트 PDF | 소규모 이사에서의 보급 비중 **unknown** |
| 종이·손글씨·캡처 이미지 | 각 사용 비중 **unknown** |

**추정:** 계약 직전 이미 받은 문장을 붙여넣는 입력은 준비 부담을 줄일 수 있다. 다만 “문자·카카오톡 견적이 일반적이므로 실제 사용 순간에 더 맞는다”는 결론은 아직 낼 수 없다.

권장 입력 경로는 다음과 같다.

| 입력 | 처리 경로 | 확인할 것 |
|---|---|---|
| 문자·대화 텍스트 | 원문 붙여넣기 → 필드 초안 → 원문 옆 교정 | 업체 발언·사용자 질문 구분, 조건 누락 여부 |
| 선택 가능한 PDF 텍스트 | 텍스트 추출 → 페이지와 원문 보존 → 교정 | 열 순서·표·금액 연결 오류 |
| 짐 목록 | 품목·수량 직접 입력 또는 목록 붙여넣기 | 실제 운송할 짐과 수량을 사용자 확정 |
| 현장 조건 | 출발·도착 구조화 폼 | 모르는 값은 `모름` 유지 |
| 업체 답변 | 문의 회차에 연결해 붙여넣기 | 업체·질문·답변 관계 |
| 이미지·스캔 PDF만 있음 | 직접 전사·구조화 입력 안내 | 텍스트 모델이 읽었다고 표시하지 않음 |

텍스트 전용 전제에서는 **방 사진에서 짐을 추출하던 D003·D004의 흐름도 변경해야 한다.** `photoIds`는 필수 근거로 삼지 않고, 사용자 확인 짐 목록을 기준으로 대조한다. 텍스트 입력용 프롬프트에서는 기존 `count`의 “가장 그럴듯한 값” 지시도 제거한다.

이번 핵심 구현은 붙여넣기와 직접 입력에 집중하고, PDF 파일 업로드는 추출기·페이지 근거 검증이 준비되면 추가할 것을 제안한다. OCR은 별도 기술 범위이므로 현재 텍스트 모델의 기능으로 설명하지 않는다.

입력 경로 적합성을 판단하려면 후속 조사에서 **사용 허락을 받고 개인정보를 가린 실제 견적 예시와 수신 채널**을 확보해야 한다. 현재 적합성은 **unknown**이다.

**5. 심사위원에게 문제 해결을 보여 주는 30초 장면**

다음은 **합성 시연 시나리오**다. 실제 피해 사례나 서비스 성능 수치로 제시하지 않는다.

입력: 총액 25만 원·계약금 5만 원 견적. 차량·인원·나머지 조건은 기재돼 있고, 책장 포함 여부·출발지 3층 계단 비용·추가비 조건 **3항목만 미확인**이다.

| 시간 | 화면과 행동 | 보여 주는 해결 |
|---|---|---|
| 0~6초 | 상단 `계약 전 확인 남음 3`과 중앙 세 행 표시 | 사용자가 송금 전에 무엇을 물어야 하는지 즉시 파악 |
| 6~12초 | 세 항목 확인 요청문을 복사하고, 발송했다고 기록 | 막연한 경고를 구체적인 문의로 전환 |
| 12~20초 | 답변 입력: “책장 1개 운송은 25만 원에 포함입니다. 출발지 3층 계단 비용은 당일 보고 정하겠습니다.” | 에이전트가 부분 답변을 항목별로 연결 |
| 20~26초 | 책장 포함 후보·계단 조건부 답변을 원문과 함께 검토하고 승인 | 근거와 사람 확인을 거쳐 반영 |
| 26~30초 | `확인 남음 2`, 계단 비용·추가비 조건만 후속 문의로 남음 | 답변이 와도 미답·조건부 항목을 지우지 않음 |

발표 문장:

> “업체가 답했다고 확인을 끝내지 않습니다. 로컬 에이전트가 답변을 항목별로 연결하고, 원문 검증과 사용자 승인을 거쳐 답한 부분만 반영합니다. 소비자는 계약금을 보내기 전에 아직 물어야 할 두 가지를 확인할 수 있습니다.”

이 장면으로 입증할 것은 **미확인 조건 발견 → 구체적 문의 → 부분 답변 구분 → 남은 확인 유지**다. 실제 추가요금 감소 효과, 지정 로컬 모델의 정확도·속도, 주최기관별 평가 선호는 **unknown**이다.
