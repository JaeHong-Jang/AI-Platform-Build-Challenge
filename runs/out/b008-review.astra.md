**검토 의견: 문제 정의와 방향에는 찬성하지만, D006은 수정 후 조건부 승인 대상이다.** 현재 코드에서 “확인되지 않은 내용을 확인됨으로 바꾸는” 경로를 재현했다. 이 상태에서 장면과 에이전트 수를 앞세우면 핵심 약속보다 연출이 먼저 평가될 위험이 있다.

다른 지휘부 리뷰는 열지 않았다. 아래 구현 사실은 지정 문서·코드를 기준으로 하며, 심사 반응과 사업성 판단은 **추정**이다. 실제 평가 기준·지불의사·추가요금 감소 효과는 **unknown**이다.

**초안이 구체적으로 다루지 않은 치명적 문제 TOP 5**

아래 1~3은 파일 수정 없이 현재 함수를 직접 호출해 확인했다. 모델 출력 후보를 주입한 검증기 시험이며, **LLM이 해당 오류를 얼마나 자주 내는지 측정한 결과는 아니다.** 4~5는 아직 구현되지 않은 설계의 재현용 검증 시나리오다.

1. **원문이 존재한다는 이유로, 포함을 뜻하지 않는 문장이 ‘총액 포함’이 된다.**

   - 입력 원문: `냉장고 운송은 협의 후 결정.`
   - 추출 후보: `{name: "냉장고", quote: "냉장고"}`
   - 실제 결과: `status: "명시됨"`, `cost: "총액 포함"`, `ask: ""`.
   - 별도 답변 시험: `냉장고는 고객님이 직접 옮기세요.`를 `explicit_answer`로 제출하면 코드가 승인 가능한 후보로 받아들였다.
   - 원인: 발췌의 부분 문자열 존재와 일부 금지어 부재를 의미 검증으로 사용한다. 근거: `verify.ts:25`, `rules.ts:45`, `rules.ts:53`, `agent.ts:95`.
   - **필수 수정:** 조건·부정이 포함된 문맥을 보존하고, 포함을 뒷받침하는 근거가 없으면 비용은 미확인으로 유지한다. 사용자 승인이 이 검증의 대체물이 되어서는 안 된다.

2. **총액과 계약금을 뒤바꿔도 숫자 검증을 통과한다.**

   - 입력 원문: `총액 35만원, 계약금 5만원`.
   - 추출 후보: `totalAmount: 50000`, `deposit: 350000`.
   - 실제 결과: 두 값 모두 유지, `dropped: []`.
   - 원인: 각 숫자가 문서 어딘가에 있는지만 검사한다. 근거: `verify.ts:44`.
   - 추정: 이 값으로 비교표와 계약금 비율 알림을 만들면 업체 선택과 경고가 동시에 왜곡된다.
   - **필수 수정:** 숫자마다 필드·단위·원문 위치를 묶어 검증한다. “근거 없는 숫자 0”에 **잘못된 필드 귀속**도 포함한다.

3. **‘모름’을 허용할수록 점검 대상이 사라질 수 있다.**

   - 입력: 옮길 짐 `냉장고`, 운송 여부 `true`, 수량 `null`.
   - 실제 결과: 품목 카드 `[]`.
   - 현재 타입은 숫자 수량만 받으며, 비교 규칙은 `count > 0`만 통과시킨다. v0.3의 nullable 입력을 연결할 때 생기는 호환성 문제다. 근거: `types.ts:23`, `rules.ts:39`.
   - 추정: 점검 대상이 줄면서 `확인 완료 N/M`만 좋아 보일 수 있다.
   - **필수 수정:** 수량 미확인 품목도 카드로 유지한다. “검토한 항목의 진행률”과 “아직 파악하지 못한 조건”을 따로 표시한다.

4. **빈칸 수가 적은 업체를 강조하면, 자세히 설명한 업체가 불리해질 수 있다.**

   - 재현 시나리오: A는 `현장 추가비 발생 가능` 한 줄, B는 계단·주차·운반거리 조건을 각각 적는다.
   - 현재 규칙은 추가비 문구마다 카드를 만든다. 기반안은 미확인 항목이 적은 순으로 정렬한다. 따라서 다른 조건이 같다면 A의 모호한 한 줄이 B의 상세한 세 줄보다 유리해질 수 있다.
   - 근거: `rules.ts:114`, `b008-design.sonnet.md:108`.
   - **필수 수정:** 업체별 생성 카드 수로 우열을 정하지 않는다. 공통 점검 항목을 행으로 고정하고, 명확한 별도 비용과 모호한 비용을 구분한다. 기본 순서는 입력 순으로 두고 자동 강조를 없앤다.

5. **공공 목록의 업체명 일치가 계약 상대방 확인으로 오인될 수 있다.**

   - 재현 시나리오: 견적에 목록과 같은 상호만 적고 등록 식별정보를 생략한다. 현재 제안대로 이름 정규화 후 완전 일치시키면 긍정적인 목록 칩이 붙는다.
   - 추가 시나리오: `구분` 값이 일반화물·미확인인 행을 이사 후보로 노출한다.
   - 실제 자료에 이런 행이 있는지는 **unknown**이다. 상호 일치 방식은 제안돼 있지만 `구분` 값은 아직 미확인이라고 기록돼 있다. 근거: `b008-design.sonnet.md:110`, `b008-data-peer.sonnet.md:56`.
   - **필수 수정:** “동일 상호 기록 있음·동일 업체 미확인”을 구분하고, 업종·영업상태를 확인한 행만 후보로 사용한다. 공개 시연의 가상 견적을 실존 업체에 연결하지 않는다.

**심사·사업성 관점**

추정: 이 설계의 가장 강한 설명은 **“AI가 견적과 답변을 읽고, 규칙이 확인 근거를 검사해 계약 전에 남은 질문을 알려 준다”**이다. LLM 3·규칙 7을 정직하게 밝히는 것은 강점이다. 다만 “규칙이 환각을 완전히 차단한다”는 주장은 위 재현 결과와 맞지 않는다. 검증 범위와 남은 실패를 함께 보여 줘야 신뢰를 얻는다.

추정: 관악구 자료의 의미는 **지역의 공개 행정정보를 소비자의 확인 행동에 연결하는 구체적 사례**라는 데 있다. 주최 기관과 지역이 같다는 이유로 가점을 기대하거나, 공공데이터 등재를 공인 추천처럼 표현해서는 안 된다. 자료 출처는 [관악구 허가업체 현황](https://www.data.go.kr/data/15080952/fileData.do)이며, 이 리뷰는 기존 조사 기록을 검토한 것으로 최신 데이터 재확인은 하지 않았다.

추정: 사업성 설명은 초기 사용자에게 도달하는 경로부터 제시하는 편이 낫다. 대학생·청년 대상 이사 안내와 연계하는 것은 **검증할 유입 가설**로 쓸 수 있다. 실제 제휴·사용 수요·수익성은 unknown이다. 업체 비교의 중립성을 강조하면서 광고·소개 수수료를 수익모델로 넣는다면 이해충돌 처리도 설명해야 한다.

**기획서 권장 순서**

1. **문제·사용자·개입 시점:** 계약금 송금 전, 견적의 빈칸을 발견하지 못하는 소규모 이사 소비자.
2. **대표 사례의 전후:** 모호한 견적 문구 → 확인 질문 → 조건부 답변 유지 → 명확한 답변 근거 확인. 실측 전에는 추가요금 감소를 성과로 쓰지 않는다.
3. **핵심 이용 흐름:** 조건 입력 → 업체 미선택 홈 → 견적별 질문·답변 → 동일 항목 비교 → 업체 선택·계약 점검.
4. **AI의 역할과 검증:** LLM 3개 역할, 규칙 7개 역할, 원문 추적, 사람 승인, 오류 사례.
5. **장면·레일·근거 그래프:** 앞의 판단 과정을 이해시키는 화면으로 설명한다.
6. **데이터·이용 조건:** 사용자 입력, 관악구 목록의 범위·기준일·접근 방법·이용 조건, 참고 조항의 확인 판본, 외부 코드 출처.
7. **구현·검증 계획:** 현재 구현/계획 구분, 역할 분담, 핵심 평가셋, 사전 구현 허용·불허 각각의 당일 범위.
