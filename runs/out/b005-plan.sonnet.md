작성 기준: `b005-evidence.sol.md`(피해 통계·약관·분쟁), `b005-benchmark.sonnet.md`(경쟁 서비스)를 먼저 읽고, 아래 기술·약관 근거를 웹에서 직접 열어 보강했다. Sol의 계획서는 보지 않았다.

## 0. 먼저 알아야 할 한계 (이번 조사에서 못 한 것)
- **이사화물 표준약관 원문(공정위 제10035호) 전문은 직접 열지 못했다.** yesform 사본은 인코딩이 깨졌고(https://www.yesform.com/wdata/doc-24229.php), 다른 사본 PDF는 접속이 거부됐다. 조항 번호는 법제처 생활법령정보 페이지를 요약 경유로 확인한 것이다(https://m.easylaw.go.kr/MOB/CsmInfoRetrieve.laf?ccfNo=3&cciNo=1&cnpClsNo=1&csmSeq=629). 제출 전에 공정위 표준약관 게시판(https://www.ftc.go.kr/www/cop/bbs/selectBoardList.do?key=201&bbsId=BBSMSTR_000000002320&bbsTyCode=BBST01)에서 제10035호 원문과 조항 번호를 대조해야 한다.
- **이삿짐 부피·톤수의 공식 기준은 찾지 못했다**(`unknown`). 검색에서 국토부·소비자원 고시 모두 나오지 않았고, 업체 블로그끼리도 기준이 다르다(아래 8절).
- **한국어 견적서 OCR의 공개 벤치마크는 찾지 못했다.** 자체 평가셋으로 재야 한다(9절).
- **본선 규칙상 사전 구현(11/2~11/25 사이 코딩)이 허용되는지 `unknown`.** 안전하게 "당일 처음부터 만들 수 있는 최소 범위"로 설계하고, 사전 준비는 프롬프트·규칙 JSON·평가 데이터·화면 설계까지로 한정한다. 주최 측 공지로 확인 필요.

## 1. 한 줄 정의와 차별점

**한 줄 정의:** 이미 받은 이사 견적서를 내 짐 사진과 대조해, 이삿날 "이건 추가요"가 나올 자리를 계약 전에 찾아내고 업체에 보낼 확인 문구로 바꿔 주는 소비자 편 웹 도구.

| 기존 | 확인된 범위 | 우리가 더하는 것 |
|---|---|---|
| Yembo | 고객이 폰으로 촬영 → 물품 탐지·부피·무게 → 번호 매긴 인벤토리를 고객이 승인해 분쟁을 줄인다고 설명. 이사업체·보험사 대상 도구(https://yembo.ai/moving/surveys) | 업체가 만든 인벤토리가 아니라 **소비자가 받아 온 외부 견적서**가 입력 |
| Agoyu | 영상 → 짐 인식 → 업체 최대 25곳 견적. 추가비용 가능 품목 표시, 인벤토리를 파손 증거로 활용(https://www.koreadaily.com/article/20260722180256503). 미국·푸에르토리코 시장 | 자사 마켓이 아닌 **한국 이사 시장의 임의 업체 견적서**를 한국 표준약관 규칙에 대입 |
| 미소 방문견적 | 서울 한정, 플래너 방문 + 영상 촬영 + 분쟁 증빙(https://magazine.hankyung.com/job-joy/article/202511132159d) | 방문 없이 사용자가 직접 올림, 견적서 문구 대조 |
| 내집이사·노블로지스 | 사진 → 품목 인식·견적(보도) (https://www.startupn.kr/news/articleView.html?idxno=30481, https://m.news.nate.com/view/20260909n33830) | 짐 인식은 입력 단계일 뿐, 핵심은 견적서와의 **차이 표시** |
| 숨고·짐싸 등 비교 앱 | 사진 입력으로 여러 견적 수신. 사다리차·분해비 등 추가요금 5항목 사전 확인은 블로그에서 권고(https://soomgo.com/blog/moving/이사견적/ 검색 스니펫) | 권고를 개인별 견적서에 자동 적용 |

검증 수준: 위 표는 "내가 연 공식 페이지·보도 기준으로 외부 견적서 대조 기능을 못 찾았다"는 뜻이지 "세상에 없다"가 아니다. 위매치·이사방·모두이사·영구크린은 미확인(benchmark 0절). 기획서에는 "확인한 서비스 범위에서"라는 단서를 붙인다. 추정: B2B 구조상 업체 견적서를 소비자 편에서 파고드는 기능을 넣을 유인이 적을 수 있다.

## 2. 사용자와 사용 순간

**주 사용자:** 포장이사·반포장이사를 처음 혼자 계약하는 20~30대 1~2인 가구. 근거: 2025년 소규모 이사 피해구제 241건 중 20~30대 65.1%(한국소비자원, https://www.kca.go.kr/kca/sub.do?menukey=5293&mode=view&no=1004455170). 주의: 이는 피해구제 신청자 구성비이고 청년 전체의 피해율이 아니다. 같은 자료에서 방문견적 없는 비대면 계약이 취약하다고 지적.

| 순간 | 사용자가 하는 일 | 우리 도구 역할 | 우선순위 |
|---|---|---|---|
| 견적 받을 때 (1~3일 전, 2~3곳 수신) | 견적서·계약서 사진 업로드 | 견적서 항목 추출, 필수 기재사항 누락 표시 | 핵심 |
| **계약 직전** | 방 사진 업로드 → 대조 | 누락·모호 항목, 업체에 보낼 확인 문구 | **가장 핵심(여기서 막는다)** |
| 이사 당일 | 추가 요금 요구를 받음 | 계약서 문구·약관 조항 근거 카드(한 화면) | P1 |
| 이사 당일 인수·인도 | 파손 발견 | 사진 기록, 사고증명서 요청 안내 | P1 |
| 입주 후 | 30일 내 통지 | 통지 기한 안내 | P2 |

근거: 표준약관 18조 1항(일부 멸실·훼손은 인도일부터 30일 이내 통지)·19조(사고증명서 1년 내 요청) (요약 경유, m.easylaw 위 URL). 소비자원 권고도 사실확인서 요구와 사진 증빙 확보(위 kca URL).

## 3. 핵심 기능 (P0 / P1 / P2)

### P0 (본선 당일 반드시 시연되는 최소 경로)
| # | 기능 | 입력 → 처리 → 출력 |
|---|---|---|
| P0-1 | 방 사진→짐 목록 | 방별 사진 3~8장 → 멀티모달 LLM이 가구·가전·대형 품목과 수량을 JSON으로 → **사용자 확인 화면**(수량 ±, 추가·삭제, "확신 낮음" 표시) |
| P0-2 | 견적서·계약서 사진→항목 추출 | 견적서 사진/PDF → LLM이 스키마 고정 JSON 추출(업체명, 사업자번호, 일시, 출발·도착지, 층수·엘리베이터·사다리차, 차량 톤수·대수, 인원, 포장·정리 여부, 포함 품목 문구, 운임 합계, 계약금, 특약) + 각 필드 "원문 위치(문장 인용)" |
| P0-3 | 대조·위험 표시 | 규칙 엔진(코드)이 8절 규칙을 적용 + LLM이 "짐 목록 vs 견적서 포함 품목/문구" 의미 대조 → **위험 항목 리스트**(누락, 모호 문구, 짐 목록에 있는데 견적서에 근거가 없는 것) |
| P0-4 | 업체 확인 문구 생성 | 위험 항목 → "사다리차 사용 및 비용은 ○원에 포함으로 확정 기재 부탁드립니다" 형태의 복사 가능한 문자/카톡 문구 + 근거 조항(표준약관 번호) 각주. 면책 문구 고정 |

### P1 (시간이 되면, 시연 보강)
| # | 기능 | 설명 |
|---|---|---|
| P1-1 | 이삿날 근거 카드 | 상황 선택("짐이 많다/사다리차 추가/식대 요구") → 내 계약서 문구 + 약관 조항(제8조 2·3항, 5조 3항) 한 화면. 인쇄 없이 모바일 전체 화면 |
| P1-2 | 링크 공유 | 결과 페이지를 무작위 토큰 URL로 업체/가족에 공유(24h 만료) |
| P1-3 | 인수 전 짐 상태 스냅샷 | P0-1에서 이미 올린 방 사진을 날짜와 함께 보존 → 파손 분쟁 증빙(추가 입력 비용 0) |
| P1-4 | 영상 입력 | 짧은 영상 → 클라이언트에서 프레임 추출해 사진처럼 처리(5절 근거) |

### P2 (기획서에 "향후"로만 쓴다)
- 업체 간 견적서 비교표, 입주·퇴거 흠집 기록, 보험(이사화물배상책임보험) 가입 여부 안내, 영어 지원.

### 흠집 기록 결합 여부 — 결론: **이사 당일 짐 상태 기록은 결합(P1), 임대차 퇴거 보증금 흠집 기록은 제외(P2)**
이유: ① 이사 당일 파손은 같은 방 사진을 재사용하므로 추가 개발이 거의 없고 소비자원 권고(사진 증빙)와 직접 연결. ② 보증금 흠집은 상대(임대인)·법적 근거(임대차)·사용 시점이 다른 별개 문제라 메시지가 흐려진다. benchmark도 (e)를 부가 기능으로 낮추자고 판정(추정 포함). 한국 임대차 사진기록 서비스는 한 건도 찾지 못함(benchmark 3절).

## 4. AI가 하는 일 vs 규칙이 하는 일 vs 사람이 확인하는 일

| 단계 | AI(멀티모달 LLM) | 규칙(코드) | 사람(사용자) |
|---|---|---|---|
| 방 사진 → 품목 | 품목명·수량·크기 등급(소/중/대) 후보, 확신도 | 대형·특수 품목 사전(양문형 냉장고, 침대 프레임, 소파, 피아노, 안마의자 등)으로 정규화 | **수량·품목 확인/수정 (필수 단계)** |
| 견적서 → 항목 | 필드 추출, 원문 인용 | 필수 기재사항 체크리스트(제4조) 누락 판정, 금액 합계·계약금 10% 계산 검증 | 추출값이 사진과 다르면 수정 |
| 대조 | 견적서 문구 vs 품목 의미 매칭("침대" vs "가구 일체") | 층수·엘리베이터·사다리차·주차 거리 입력값에 따른 질문 트리거 | 현장 조건(층·엘리베이터·주차) 직접 입력 |
| 위험 판정 | 문구가 모호한지 설명 | **조항 인용과 위반/주의 판정은 규칙 테이블이 한다.** LLM이 약관 내용을 생성하지 않게 한다 | 업체와 합의한 사항 확인 |
| 문구 생성 | 어조 다듬기 | 근거 조항 번호는 규칙에서 주입 | 업체에 보낼지 결정 |
| 부피·톤수 | 정확한 ㎥ 산출은 시도하지 않는다 | 차량 톤수는 견적서 값을 그대로 인용 | 업체에 차량 구성 질문 |
| 법적 판단 | 하지 않음 | "표준약관 기준 안내"로 고정 | 분쟁 시 1372·소비자원 상담 |

원칙: **AI는 읽고 후보를 낸다. 규칙이 판정하고 근거를 단다. 사람이 확정한다.**

## 5. 웹 vs 앱 결정

**결론: 모바일 웹(반응형, PWA 설치 비의존). Next.js 등 웹 스택 단일 코드베이스.**

| 기준 | 모바일 웹 | 네이티브 앱 | 하이브리드(RN/Flutter) | 비고/근거 |
|---|---|---|---|---|
| 카메라·사진 | `<input type=file accept="image/*" capture>`로 OS 카메라 호출, 없으면 파일 선택으로 폴백. MDN: capture는 "Limited availability"이므로 폴백 필수 | 최상 | 상 | https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/capture |
| 실시간 카메라 스트림 | getUserMedia: iOS Safari 11+ 지원, 보안 출처(HTTPS) 필수 | - | - | https://caniuse.com/stream |
| 영상 녹화(브라우저 내) | MediaRecorder: caniuse는 iOS Safari 14.5부터 기본 활성이라 표기. WebKit 블로그는 iOS 14.3 베타부터 기본 활성이라 해서 **출처 간 불일치**, 둘 다 현행 iOS 대비 충분히 오래됨 | 최상 | 상 | https://caniuse.com/mediarecorder , https://webkit.org/blog/11353/mediarecorder-api/ |
| 영상 업로드 한계 | `capture` 영상은 iOS에서 최대 10분에서 녹화 종료(Apple 포럼 보고, 해결책 없음). 우리는 방 사진 중심이라 영향 작음 | 네이티브는 설정 가능 | 가능 | https://developer.apple.com/forums/thread/655193 |
| 홈 화면(PWA) 카메라 | 과거 홈 화면 앱에서 getUserMedia 실패 버그(iOS 13.4에서 수정 언급), 현재도 "닫았다 다시 열면 녹화 안 됨" 보고 존재 → **PWA 설치에 의존하지 않고 일반 Safari/Chrome 탭에서 쓰게 한다** | - | - | https://bugs.webkit.org/show_bug.cgi?id=185448 , https://developer.apple.com/forums/thread/797987 |
| 이사 당일 현장 사용 | 링크 하나면 열림, 설치 불필요 | 설치 필요 | 설치 필요 | 추정: 이사 당일 급할 때 앱 설치는 장벽 |
| 업체와 링크 공유 | URL 그대로 | 딥링크/스토어 필요 | 동일 | 핵심 사용 사례(견적 확인 문구 공유) |
| 팀 강점 | 웹 | 학습 필요 | 학습 필요 | 주어진 조건 |
| 9시간 구현 | 배포(Vercel 등)까지 1단계 | 스토어 심사·서명 부담 | Expo Go면 가능하나 스택 추가 | 추정 |
| 심사 시연 | 심사위원 폰으로 QR 접속 | 설치 선행 | 설치 선행 | 추정 |

네이티브가 필요한 경우(푸시 알림, 백그라운드 촬영, 긴 영상)는 MVP 범위 밖이다. iOS 홈 화면 PWA는 카메라 안정성 이슈가 있어 **"설치하세요"를 안내하지 않는 것이 결정이다.**
위험: iOS `capture` 입력은 HEIC 사진을 반환할 수 있다(추정: 확인 필요). 클라이언트에서 canvas로 JPEG 리사이즈(긴 변 ≤1568px)해 올리면 EXIF 위치정보 제거, 용량 절감, 모델 입력 호환(Claude는 JPEG/PNG/GIF/WebP만 지원: https://platform.claude.com/docs/en/build-with-claude/vision)이 동시에 해결된다. **사전에 iPhone·Android 실기기에서 반드시 검증**(11월 준비 기간 1순위 과제).

## 6. 기술 구조

| 층 | 선택 | 이유 |
|---|---|---|
| 프런트 | Next.js(React) + Tailwind, 모바일 우선 | 팀 강점, 배포 단순 |
| 백엔드 | Next.js Route Handler(서버리스) | API 키를 서버에 보관, 파일 처리 |
| AI | 멀티모달 LLM 한 종류를 기본으로 하고 교체 가능하게 얇은 어댑터 1개. 후보: Claude 비전(공식: 요청당 이미지 100장·장당 10MB·8000px 한도, 이미지 PDF 모두 입력 가능. https://platform.claude.com/docs/en/build-with-claude/vision , PDF 최대 32MB·600쪽 https://platform.claude.com/docs/en/build-with-claude/pdf-support), Gemini(영상 직접 입력 가능, 기본 1 FPS 샘플링, 인라인 요청 20MB 이내 권장, Files API 사용 시 대용량 https://ai.google.dev/gemini-api/docs/video-understanding) | 별도 OCR 서비스를 두지 않고 견적서 사진도 같은 모델이 읽는다(배선 최소화). 결과는 JSON 스키마 강제 |
| 별도 OCR(선택) | Naver CLOVA OCR, Upstage Document OCR(한국어·영어 특화, 단어별 신뢰도 제공: https://console.upstage.ai/docs/capabilities/document-ocr) | 모델 OCR이 금액·사업자번호에서 틀릴 때만 보조로 추가(9시간 안에는 P2). 정확도 수치는 공개 벤치마크 없음 |
| 저장소 | MVP는 **서버 저장 없이 세션 처리**(이미지는 응답 후 폐기) + 공유 링크용 결과 JSON만 Postgres(Supabase)/KV에 24h TTL | 개인정보 최소화 |
| 규칙 데이터 | `rules.json`(8절). 코드가 읽는 정적 파일 | LLM이 약관을 지어내지 못하게 |

**데이터 흐름(텍스트)**
```
[폰 브라우저] 방 사진·견적서 사진 선택
   → canvas로 리사이즈·JPEG 변환·EXIF 제거(클라이언트)
   → POST /api/analyze (HTTPS)
[서버] ① 방 사진 → LLM → items[] (품목,수량,확신도)
       ② 견적서 → LLM → quote{필드, 원문 인용}
   → [화면] 사용자 확인·수정 (items, quote, 현장조건)
   → POST /api/compare
[서버] ③ 규칙 엔진(rules.json) → 체크 결과 + 조항 번호
       ④ LLM → 의미 대조(짐 vs 견적 문구) → 위험 항목
       ⑤ LLM → 확인 문구 초안(조항 번호는 규칙이 주입)
   → [화면] 위험 리스트 · 문구 복사 · (P1) 근거 카드 · 공유 링크
```

**개인정보 원칙(집 내부 사진·견적서)**
- 수집 최소화: 서버에 원본 이미지를 저장하지 않는 것을 기본값으로 한다(분석 후 폐기). 저장이 필요한 기능(P1-3 스냅샷, 공유 링크)은 **옵트인**과 만료 시간을 둔다.
- 사진에서 얼굴·우편물·운송장 등 개인 식별 정보는 올리지 말라고 업로드 화면에 안내(모델이 사람을 식별하지 못하는 것은 Anthropic 사용 정책에 따름이지만, 우리가 막는다고 쓰지 않는다).
- 모델 제공사 처리: Anthropic 공식 FAQ는 "업로드 이미지는 요청 처리 후 저장되지 않으며 모델 학습에 쓰지 않는다"고 설명(https://platform.claude.com/docs/en/build-with-claude/vision , FAQ). 다른 사업자를 쓰면 그 약관을 따로 확인해야 한다.
- 시연·평가용은 팀이 직접 만든 방 사진과 가상 견적서만 사용한다. 실제 이용자 문서를 평가셋에 넣지 않는다.
- EXIF(촬영 위치)는 클라이언트 재인코딩으로 제거한다.

## 7. 기술 근거

**(1) VLM의 가구·가전 식별과 수량**
- 공식 문서의 한계 기술: "Claude can give approximate counts of objects in an image but might not always be precisely accurate, especially with large numbers of small objects." / "Claude's coordinate and localization outputs are approximate" / 저화질·회전·200px 미만 이미지는 환각 가능 / "Do not use Claude for tasks requiring perfect precision ... without human oversight" (https://platform.claude.com/docs/en/build-with-claude/vision, Limitations).
- 논문: Visual Enumeration Remains Challenging for Multimodal Generative AI(https://arxiv.org/abs/2402.03328) — 초록 기준 "가장 진보한 모델도 단순 자극에서 개수를 신뢰성 있게 말하지 못한다", 모델 크기 키우기만으로는 부족하다는 결론. GPT-4V 73.9%, Gemini 70.6%라는 수치는 검색 요약에서만 봤고 원문에서 확인하지 못했다(`unknown`, 인용 금지).
- 물체 종류가 섞이면 정확도가 떨어진다는 보고: VLMCountBench(https://alphaxiv.org/abs/2510.04401 검색 요약만 확인, 추정으로 취급).
- 가정 환경 가구 인벤토리 정확도를 직접 측정한 공개 벤치마크는 찾지 못했다(`unknown`). Yembo·Agoyu의 정확도 수치도 공식 자료에서 확인하지 못했다(`unknown`).
- 영상: Gemini 기본 1 FPS 샘플링이라 빠른 움직임에서 디테일을 놓칠 수 있다고 공식 문서에 명시(https://ai.google.dev/gemini-api/docs/video-understanding). 천천히 한 바퀴 도는 방 촬영은 문제가 작지만, **MVP는 사진 우선, 영상은 클라이언트 프레임 추출**로 한다.

**부피·개수 한계와 우회:** 이미지 한 장으로 ㎥·kg을 정밀 산출하지 않는다. ① 대형 품목(침대, 냉장고, 소파, 옷장, 세탁기 등)만 "품목명+수량+크기 등급"으로 뽑고, ② 사용자가 수량을 확인·수정하는 단계를 **필수 UX**로 두며, ③ 견적서의 차량 톤수·인원은 업체 값을 그대로 인용하고 "이 구성으로 아래 품목이 다 실리는지 업체에 확인" 문구만 생성한다. 즉 "부족하다"고 단정하지 않고 "확정 기재를 요구한다".

**(2) 문서 OCR**
- 한국어 견적서에 대한 독립 벤치마크는 찾지 못했다(`unknown`). 참고: 업체 자체 시험에서 Upstage 구 Document AI OCR이 보험 서류 7종 평균 약 95%(회사 주장, 이사 견적서와 무관, https://en.content.upstage.ai/newsroom/documentai-samsunglife 검색 요약). 한국어 OCR 정확도를 CLOVA 97~99%로 소개한 블로그는 측정 방법이 불명확하다(https://www.lido.app/kr/hangugeo-ocr). **인용하지 않는다.**
- 따라서 "견적서 필드 추출 정확도"는 우리가 평가셋으로 직접 잰 값만 기획서에 쓴다. 핵심 필드(금액, 사업자번호, 차량·인원, 사다리차 유무)는 사용자 확인 화면에서 교정한다.
- 이미지 품질 가이드: 글자가 작으면 환각 가능, 과도한 JPEG 압축은 글자 판독을 해친다(Claude 문서 Image quality guidance). 견적서 촬영 안내 문구와 압축 품질 상한(≥0.85)을 UI에 반영.

### 8-3. 짐 부피·톤수의 공식 기준
- **공식 기준은 찾지 못했다(`unknown`).** 검색에서 국토부·소비자원 기준이 나오지 않았다.

- 그래서 우리는 톤수를 계산하지 않는다. **"차량 톤수·대수가 견적서에 확정 기재되어 있는가"와 "대형 품목이 몇 개인가"만 대조하고, 업체에 확인하게 한다.** 2011년 분쟁 사례(품목명만으로 부피를 판단해 차량 1대 추가 요구)와 같은 구조를 겨냥(Sol 조사의 소비자원 사례).

## 9. 평가 방법과 성공 지표

**평가셋(전부 팀이 직접 만든다, 실제 개인 문서 사용 금지)**
- 방 사진: 서로 다른 방 12곳 × 3~5장(원룸 6, 투룸 4, 아파트 거실 2). 각 방은 손으로 정답 품목 목록(품목, 수량) 작성. 조명·가려진 정도 다양화.
- 견적서: 가상 견적서 20장(5절 필수항목 일부를 의도적으로 누락한 것 10, 정상 5, "현장 추가 가능" 같은 모호 문구 5). 사진 촬영본·스크린샷·PDF를 섞는다.
- 계약서 문구 시나리오 10건(R2, R5, R6 위반 유형).
- 모든 정답은 평가 전에 고정(결과를 보고 정답을 바꾸지 않는다).

## 13. 기획서 문장 초안 (대회 권장 5항목)

**① 문제와 주요 사용자**
이사를 혼자 계약하는 20~30대는 방문견적 없이 전화·온라인으로 견적을 받는 경우가 많아, 이삿날 "짐이 많다"는 이유로 추가 요금을 요구받는 일이 생깁니다. 한국소비자원이 2025년 소규모 이사 피해구제 241건을 분석한 결과 신청자의 65.1%가 20~30대였고, 접수된 피해 유형 중 추가 비용 요구는 70건(24.9%, 유형별 집계 기준)이었습니다. 공개 사례에는 85만 원에 계약한 뒤 당일 50만 원을 추가로 요구받은 경우도 있습니다. 문제는 계약 전에 견적서가 무엇을 포함하는지 확인하기 어렵다는 점입니다. 주요 사용자는 포장이사를 처음 혼자 계약하는 1~2인 가구 청년입니다. (출처: 한국소비자원 https://www.kca.go.kr/kca/sub.do?menukey=5293&mode=view&no=1004455170)

**② 핵심 기능과 이용 흐름**
사용자는 먼저 방 사진을 올려 AI가 뽑은 짐 목록을 확인하고 수정합니다. 이어 받은 견적서를 촬영하면 업체명, 차량·인원, 사다리차 포함 여부, 총액이 추출됩니다. 서비스는 짐 목록과 견적서를 대조해 "견적서에 근거가 없는 항목"과 "현장에서 추가될 수 있는 모호한 문구"를 표시합니다. 각 항목에는 이사화물 표준약관의 해당 조항이 붙고, 업체에 보낼 확정 문구가 생성됩니다. 이삿날에는 같은 결과를 근거 카드로 한 화면에 보여 줍니다.

**③ AI 적용 방식·활용 데이터·기술 구성**
멀티모달 LLM API로 방 사진 속 가구·가전을 인식하고 견적서 사진에서 항목을 추출합니다. 약관 조항을 근거로 한 위험 판정은 LLM이 아니라 규칙 데이터가 맡아, AI가 약관을 지어내지 않게 합니다. 부피를 AI가 단정하지 않고 사용자가 품목·수량을 확인하는 단계를 둡니다. 데이터는 팀이 직접 만든 방 사진과 가상 견적서, 공정거래위원회 이사화물 표준약관과 소비자분쟁해결기준 공개 조항만 사용하며, 이미지는 분석 후 서버에 저장하지 않는 것을 기본으로 합니다. 프런트·백엔드는 Next.js 모바일 웹이며, 링크 하나로 업체와 공유할 수 있습니다.

**④ 구현 계획·역할·기대 효과**
본선 당일에는 9시간 안에 방 사진→짐 목록→견적서 추출→대조→확인 문구의 핵심 경로를 구현하고 3분 시연합니다. 사전 준비에서는 직접 만든 평가셋으로 품목 재현율, 견적서 필드 정확도, 누락 탐지율, 오탐을 측정해 있는 그대로 공개합니다. 팀원은 프런트, AI·규칙 백엔드, 평가·문서 역할로 나눕니다. 기대 효과는 소비자가 계약 전에 모호한 문구를 확정 문구로 바꿔 이삿날 분쟁 요인을 줄이는 것입니다. 효과 크기는 평가 전에는 주장하지 않습니다. 본 서비스는 법률 자문이 아니라 표준약관 기준의 확인 도구입니다.

**⑤ 외부 자료·오픈소스·AI 도구 출처**
한국소비자원 소규모 이사 주의보(https://www.kca.go.kr/kca/sub.do?menukey=5293&mode=view&no=1004455170), 법제처 생활법령정보 이사화물 표준약관 안내(https://www.easylaw.go.kr/CSP/CnpClsMain.laf?ccfNo=3&cciNo=1&cnpClsNo=1&csmSeq=629), 공정거래위원회 이사화물 표준약관 제10035호(https://www.ftc.go.kr/www/cop/bbs/selectBoardList.do?key=201&bbsId=BBSMSTR_000000002320&bbsTyCode=BBST01), 국가법령정보센터 화물자동차 운수사업법 시행규칙(https://law.go.kr/LSW/lsLinkCommonInfo.do?lspttninfSeq=188629), 멀티모달 LLM API(Anthropic 또는 Google Gemini, 사용 시 공식 문서 명시), Next.js 등 오픈소스 프레임워크(사용 시 라이선스 목록 첨부). 경쟁·참고 서비스는 Yembo(https://yembo.ai/moving/surveys), Agoyu(https://www.koreadaily.com/article/20260722180256503)입니다. 평가에 쓴 사진·견적서는 모두 팀이 직접 제작했습니다.
