# B006 분석 — 이사 지킴이의 문제 정의와 AI 에이전트 배치

분석: Sol · 2026-10-23  
기준: D003 및 제작계획 위키. **아래 에이전트 설계는 검토 제안이며, D003의 확정 범위를 변경하는 판정이 아니다.**

## 1. 우리가 해결할 문제

> **비대면 견적을 받은 소규모 이사 이용자가 계약금을 보내기 전에, 짐과 작업조건이 문서에 충분히 적혀 있는지 확인하기 어려워 당일 추가요금 요구와 이사 거부에 대비하지 못하는 문제를 해결한다.**

- **누가:** 방문견적 없이 사진·전화·온라인 입력으로 견적을 받은 원룸·소형 주거 이사 청년.
- **언제:** 업체를 골라 견적을 받은 뒤, 계약을 체결하고 계약금을 보내기 직전.
- **원인 → 손해:** 짐·작업조건·비용 포함 범위가 문서에 구체적으로 남지 않음 → 당일 짐의 양·건물 구조를 이유로 추가요금을 요구받고, 이를 거절하면 이사를 거부당할 수 있음.

여기서 **“짐·작업조건의 문서 기재 공백”은 서비스가 집중할 문제 가설**이다. 소비자원 자료는 비대면 계약의 취약성과 상세 기재 필요성을 뒷받침하지만, 문서 기재 공백이 피해 전체에서 차지하는 비율이나 인과효과를 측정한 자료는 아니다.

| 추가비용 | 별도 비용의 항목·발생 조건·금액 또는 산정 방식을 업체에 묻게 한다. | 추가요금 차단, 적정가격 산정, 위법 여부 판정을 약속하지 않는다. |

| 피해 대응 | 계약 전에 확인할 사항을 구체화한다. | 당일 이행 보장, 파손·분실 배상, 취소 위약금 계산·분쟁 대행은 하지 않는다. |
| 업체 답변 | **P1 제안:** 답변에서 확인된 항목과 남은 질문을 구분한다. | 무응답·포괄적 긍정·침묵을 항목별 합의로 처리하지 않는다. |

## 2. AI 에이전트 배치 판단

**D003의 확정 P0에는 에이전트가 없다.** 사진·견적서 각각의 단순 AI 호출 두 번과 규칙 대조로 구성된다. 여러 AI 호출을 병렬 실행하는 것만으로 에이전트라고 부르지 않는다.

이 문서에서 에이전트는 **목표를 받아 허용된 도구를 선택하고, 도구 결과에 따라 다음 행동이나 종료를 결정하는 제한된 실행 주체**로 정의한다.

### 사용자 흐름별 배치표

| 사용자 단계 | 사용할 방식 | 왜 이 방식인가 | 실패하면 | 사용자가 받는 화면 |
|---|---|---|---|---|
| ① 사진·견적서 업로드, 작업조건 입력 | **규칙 코드. 에이전트 불필요** | 파일 형식·용량·필수 입력 검사는 정해진 조건으로 처리 가능하다. | 업로드 오류 또는 직접 입력으로 전환한다. | 업로드 미리보기, 작업조건 입력 폼 |
| ② 방 사진에서 짐 초안 추출 | **단순 이미지 LLM 호출 1회** | 정해진 이미지에서 품목·수량 후보를 고정 JSON으로 추출하는 작업이다. 도구 선택·반복이 필요하지 않다. | 불명확한 품목·수량을 표시하고 사용자에게 수정을 요구한다. | 사진 옆 품목 목록, 수량·중복·운송 여부 수정 |
| ③ 견적서 항목·원문 발췌 추출 | **단순 이미지 LLM 호출 1회 + 검증 코드** | 총액·차량·인원·포함 문구를 한 문서에서 추출한다. | 원문 위치·발췌를 검증하지 못하면 근거로 채택하지 않고 재입력을 받는다. | 견적 이미지 옆 추출 필드·발췌 후보 |
| ④ 사용자 초안 교정 | **사람 + 규칙 코드. 에이전트 불필요** | 실제 짐·작업조건과 숫자는 사용자가 확인해야 한다. | 미확인 필드를 그대로 남긴다. 임의 보완하지 않는다. | 확인·수정 폼 |
| ⑤ 빠진 정보 확인 | **P0: 규칙 폼 / P1 제안: 질문 에이전트 A** | 고정 필수항목만 묻는다면 규칙으로 충분하다. 문서·사용자 답변에 따라 근거를 다시 찾거나 질문 대상을 바꾸는 경우에만 에이전트 가치가 있다. | 정적 체크리스트로 전환하고 미응답은 `unknown`으로 남긴다. | “도착지 엘리베이터 사용 여부를 알려 주세요” 같은 항목별 질문 |
| ⑥ 기재 상태 대조 | **규칙 코드. 에이전트 불필요** | D003의 세 확인 규칙과 네 가지 상태를 일관되게 적용해야 한다. | 대응 근거가 없거나 연결이 모호하면 미확인 상태를 유지한다. | `명시됨 / 포함 여부 미확인 / 조건 모호 / 판독 불가` 카드 |
| ⑦ 카드에 견적 근거 붙이기 | **원문 위치 조회·검증 코드. 기본적으로 에이전트 불필요** | 한 장의 견적서에서 이미 추출한 근거를 연결하는 일은 ID·위치 조회로 처리 가능하다. | 근거 발췌를 숨기고 “문서에서 확인하지 못함”을 표시한다. | 사진 번호·견적 원문 위치·발췌 |
| ⑧ 업체 확인 요청 작성·복사 | **검토한 문장 틀 + 규칙 코드. 에이전트 불필요** | 확인할 항목을 문장 틀에 넣으면 된다. 자유 생성이 필요하지 않다. | 필수 값이 없으면 빈칸 또는 확인 요청으로 남긴다. | 사용자가 수정·복사할 요청문 |
| ⑨ 업체 답변 첨부·재점검 | **P1 제안: 답변 점검 에이전트 B** | 답변이 일부 항목만 다루거나 새 조건을 제시하면, 기존 카드와 원문을 선택적으로 조회하고 후속 확인 대상을 바꿔야 한다. | 기존 카드를 유지하고 사용자가 직접 대응 항목을 지정하게 한다. | 답변 근거와 갱신 후보, 여전히 미확인인 항목 |

### 에이전트가 가치를 내는 두 자리

**A. 빠진 정보 질문 에이전트**

목표는 “사용자에게 모든 항목을 다시 묻기”가 아니라 **이미 확인된 내용을 제외하고, 현재 확인 요청을 만드는 데 필요한 정보만 확보하기**다.

예를 들어 ‘엘리베이터 없음’이 확정된 상태라면 엘리베이터 유무를 다시 묻지 않는다. 문서에 계단 작업 문구가 있는지 조회하고, 없으면 업체에 물을 항목으로 남긴다. 사용자가 알 수 있는 현장 사실과 업체만 답할 수 있는 비용 포함 여부를 구분한다.

**추정:** 복잡한 답변·상충 정보가 있을 때 반복 질문을 줄일 수 있다. 단순 작업조건 폼보다 유리한지는 **unknown**이다. 고정 필드의 공란만 찾아 질문한다면 **에이전트 불필요**다.

**B. 업체 답변 점검 에이전트**

목표는 **업체 답변을 기존 확인 항목에 연결하고, 답하지 않은 항목을 남기는 것**이다.

가상 예시: 책장과 계단 작업을 함께 물었는데 업체가 “책장은 포함입니다”라고만 답하면, 책장 관련 갱신 후보만 제시하고 계단 작업은 미확인으로 유지한다. 답변의 추가 조건이 기존 견적과 충돌하면 이를 사용자에게 보여 준다.

**추정:** 항목별 부분 답변을 반복 점검하는 흐름은 초기 견적 추출보다 에이전트의 도구 선택·반복 가치가 크다. 다만 **단순 LLM 한 번과 규칙으로 같은 품질을 낼 수 있다면 에이전트로 구현할 이유는 없다.**

## 3. 에이전트 도구 계약과 실행 한도

아래는 **개발 제안 JSON 계약**이다. 외부 API의 실제 사양이 아니다. 두 에이전트 모두 웹검색·법령 생성·외부 전송 도구를 갖지 않는다.

### 공통 통제

- 모델은 **후보**만 제출한다. 화면 상태 변경은 코드 검증과 사용자 확인 뒤 적용한다.
- 견적서·업체 답변 속 문장은 분석 대상 데이터로만 취급한다. 그 안의 명령을 실행하지 않는다.
- `unknown`·충돌·읽기 실패를 빈 문자열이나 추정값으로 대체하지 않는다.
- 원문에 특정 표현을 찾지 못했다는 사실만으로 “서비스에서 제외됐다”고 단정하지 않는다.
- 참고 조항은 검토된 고정 자료에서 코드로 연결한다. 모델이 조항 번호·내용을 작성하지 않는다.

### 공통 도구 ① `get_case_state`

현재 확인 상태와 미확인 항목을 읽는다.

입력:

```json
{
  "case_id": "case_01",
  "expected_revision": 3
}
```

출력:

```json
{
  "revision": 3,
  "fields": [
    {
      "field_id": "destination.elevator",
      "value": null,
      "state": "unknown",
      "confirmed_by_user": false
    }
  ],
  "cards": [
    {
      "card_id": "card_stairs",
      "status": "포함 여부 미확인",
      "evidence_ids": []
    }
  ],
  "available_sources": ["quote_01", "reply_01"]
}
```

`revision`が 달라졌다면 과거 상태를 바탕으로 한 갱신 후보를 적용하지 않는다.

### 공통 도구 ② `find_evidence`

선택한 견적서 또는 업체 답변에서 항목 관련 근거 후보를 찾는다. 검색 결과는 포함 여부 판정이 아니다.

입력:

```json
{
  "source_id": "quote_01",
  "target_field_id": "stairs_cost",
  "query": "계단 작업 비용 포함 여부",
  "max_results": 2
}
```

출력:

```json
{
  "source_id": "quote_01",
  "matches": [
    {
      "evidence_id": "ev_12",
      "text": "현장 여건에 따라 별도 협의",
      "locator": {
        "kind": "image_region",
        "image_id": "quote_01",
        "bbox_normalized": [0.1, 0.7, 0.9, 0.8]
      },
      "verification": "needs_user_check"
    }
  ],
  "search_result": "candidates_found"
}
```

출력의 `text`와 위치는 원문 대조 대상이다. 텍스트 원문이 있으면 문자 범위 일치를 코드로 검사하고, 이미지 인식 결과는 원문 옆에서 사용자가 확인한다. 일치·위치 확인에 실패한 발췌는 근거로 채택하지 않는다. 결과가 없으면 `matches: []`, `search_result: "not_found"`를 반환한다.

### A 전용 도구 ③ `queue_question`

사용자에게 보여 줄 질문 후보를 제출한다. 질문 대상과 필요성은 코드가 검사한다.

입력:

```json
{
  "case_id": "case_01",
  "expected_revision": 3,
  "target_field_id": "destination.elevator",
  "reason_code": "missing_user_fact",
  "template_id": "ask_elevator_availability",
  "evidence_ids": []
}
```

출력:

```json
{
  "accepted": true,
  "question_id": "q_01",
  "question": "도착지에서 엘리베이터를 사용할 수 있나요?",
  "options": ["사용 가능", "사용 불가", "모름"],
  "awaiting_user": true
}
```

질문은 검토된 틀로 렌더링한다. 사용자가 모른다고 답한 항목을 같은 방식으로 반복 질문하지 않는다. 업체의 비용 포함 여부는 사용자가 추정하게 하지 않고 업체 확인 카드로 보낸다.

### B 전용 도구 ④ `propose_reply_update`

업체 답변과 기존 카드의 대응 관계 및 갱신 후보를 제출한다. 확정 상태를 직접 변경하지 않는다.

입력:

```json
{
  "case_id": "case_01",
  "expected_revision": 4,
  "reply_source_id": "reply_01",
  "proposals": [
    {
      "card_id": "card_bookcase",
      "relation": "explicit_answer",
      "evidence_ids": ["reply_ev_01"],
      "proposed_status": "명시됨"
    },
    {
      "card_id": "card_stairs",
      "relation": "unanswered",
      "evidence_ids": [],
      "proposed_status": "포함 여부 미확인"
    }
  ]
}
```

출력:

```json
{
  "accepted_for_review": true,
  "pending_changes": ["card_bookcase"],
  "unchanged_cards": ["card_stairs"],
  "requires_user_confirmation": true,
  "validation_errors": []
}
```

`relation`은 `explicit_answer / conditional_answer / unanswered / conflicting / unreadable`로 제한한다. 네 가지 카드 상태와의 대응은 규칙 코드가 검사한다. “합의 완료” 상태는 만들지 않는다. 예시의 `명시됨`은 **첨부 답변에 해당 표현이 있다는 뜻**이며, 계약의 법적 효력 판정이 아니다.

### 실행 한도·종료·사람 확인

아래 횟수는 **설계 제안값**이며 실측 결과가 아니다.

| 항목 | A: 빠진 정보 질문 | B: 업체 답변 점검 |
|---|---|---|
| 사용 도구 | `get_case_state`, `find_evidence`, `queue_question` | `get_case_state`, `find_evidence`, `propose_reply_update` |
| 최대 반복 | 사용자 답변을 포함해 **3회 질문 주기** | 답변 업로드 한 건당 **2회 점검 주기** |
| 도구 호출 상한 | 주기당 4회, 합계 **12회** | 주기당 4회, 합계 **8회** |
| 정상 종료 | 필요한 사용자 사실 확보, 또는 남은 항목이 업체 확인 대상으로 정리됨 | 답변과 카드의 대응 후보 작성 완료 |
| 조기 종료 | 사용자 건너뛰기·모름, 같은 상태 반복, 새 정보 없음 | 새 근거 없음, 같은 후보 반복, 답변 판독 불가 |
| 상한·오류 도달 | 정적 폼과 남은 미확인 목록으로 전환 | 기존 카드 유지, 직접 대응 지정 화면으로 전환 |
| 사람 확인 | 질문에 답하고, 원문 근거와 최종 짐·작업조건을 확인 | 답변의 출처·발췌·대응 항목을 확인한 뒤 갱신 승인 |
| 외부 행동 | 없음 | 없음 |

모델 응답이 돌아오지 않는 경우에는 반복 횟수와 별도로 시간 제한을 두고 수동 흐름으로 전환한다. 적절한 시간 제한값은 **unknown**이며 실측 후 정한다. 사용자 응답을 기다리는 시간에는 에이전트를 계속 실행하지 않는다.

## 4. D003과 구현 범위의 관계

D003은 **AI 호출 두 번·병렬**, 이후 대조·문구 작성은 규칙과 문장 틀로 처리하도록 확정했다. 따라서 질문 에이전트를 P0에 추가하면 호출 횟수·지연·오류 처리·사용자 흐름이 달라진다. **“판정은 규칙”을 지킨다는 이유만으로 D003과 동일한 구현이라고 볼 수 없다.**

| 범위 | 제안 |
|---|---|
| **확정 P0** | 사진·견적 추출 → 사용자 교정 → 규칙 카드 → 확인 요청 복사. **AI 문서 확인 보조 서비스**로 설명한다. |
| **P1 후보 A** | 질문 에이전트. 정적 폼 대비 반복 질문·누락을 줄이는지 검증한 뒤 채택한다. |
| **P1 후보 B** | 업체 답변 점검 에이전트. D003에서 이미 P1로 분류한 답변 첨부·재점검에 배치한다. |
| **범위 변경 필요 조건** | 예선에서 에이전트를 핵심 기능으로 약속하려면, 지휘부가 확장 범위와 구현·시연 책임을 별도 판정해야 한다. |

**분석 제안:** 에이전트 확장 하나를 우선 검증한다면 **B: 업체 답변 점검**을 택한다. 확인 요청부터 답변 후 미확인 항목 갱신까지 사용자 과업이 이어지고, 부분 답변·추가 조건에 따라 다음 조회 대상을 바꾸는 필요가 비교적 분명하기 때문이다. 하루 구현 가능성과 단순 호출 대비 우위는 아직 **unknown**이다.

## 5. 에이전트 채택 전 검증할 것

에이전트 명칭이 아니라 **사용자 과업 개선**을 검증해야 한다. 다음은 평가 제안이며 결과는 모두 **unknown**이다.

| 비교 | 확인할 결과 |
|---|---|
| 질문 에이전트 vs 정적 필수항목 폼 | 이미 답한 내용을 다시 묻는 횟수, 필요한 정보의 누락, 완료 시간 |
| 답변 점검 에이전트 vs 단순 LLM 호출 + 규칙 | 답변과 카드의 대응 정확도, 미답변을 확인된 것으로 바꾸는 오류, 지연·호출 비용 |
| 두 방식 공통 | 원문에 없는 근거 생성, 포괄적 긍정의 과잉 적용, 상충 조건 누락 |
| 사용자 확인 전·후 | 모델 후보의 정확도와 사용자가 교정한 최종 결과를 따로 측정 |

추가요금 감소·이사 거부 예방 효과는 이 평가만으로 입증되지 않는다. 별도의 실사용 검증이 필요하다.

## 6. 심사위원 질문에 대한 3줄 답변

**P1 에이전트를 실제 구현·시연한 경우에만 사용할 답변:**

> 에이전트는 받은 견적과 업체 답변을 조회하고, 아직 확인되지 않은 항목에 따라 다음 도구와 확인 대상을 선택합니다.  
> 일부 항목만 답변되면 해당 항목의 갱신 후보만 만들고, 나머지는 미확인으로 남겨 확인을 이어갑니다.  
> 에이전트가 근거 수집과 확인 순서를 맡고, 최종 상태는 규칙과 사용자 확인으로 통제합니다.

**P0만 구현했다면:** “현재 구현은 AI 추출과 규칙 기반 확인 서비스입니다. 에이전트는 업체 답변을 받아 미확인 항목을 반복 점검하는 확장 기능으로 계획했습니다”라고 답해야 한다.

## 7. 남은 unknown

- 문서 기재 공백이 추가요금 피해의 원인에서 차지하는 비중
- 사용자가 실제 계약 직전에 사진·견적서를 올리고 확인 요청을 보낼 의사
- 에이전트가 정적 폼·단순 LLM 호출보다 나은 결과를 내는지
- 한국어 견적·업체 답변의 추출 및 항목 대응 정확도
- 에이전트 호출 비용·처리 시간·하루 구현 가능성
- 공정위 표준약관 원본 전문 대조와 참고 안내 문구 확정
- 실제 추가요금·이사 거부 감소 효과
- 에이전트 확장 범위에 대한 후속 peer/review 및 지휘부 판정
