# B008 독립 분석 — 이사 지킴이 v0.3 설계 명세

**제안: 조건 한 줄로 맞춤 홈을 만들고, 사람이 짐을 옮기는 SVG 장면과 함께 확인 결과가 쌓이는 이사 준비 관제 서비스로 설계한다. 업체는 비워 둔 상태에서 시작하고, 같은 조건으로 받은 견적과 증빙을 비교해 사용자가 고른다.**

짐 부피·필요 차량·인원·가격의 산정 근거는 `unknown`이다. 따라서 앱이 산정하는 것은 **확인한 짐의 수량, 문서 항목의 기재 상태, 남은 질문, 실제 견적 사이의 차이**다. 차량·인원·가격은 업체 원문에서 읽은 값만 표시한다. 근거: `runs/out/b008-data.sol.md:16`, `:20`, `:95`, `:163`, `:186`.

이 문서는 독립 분석안이다. 아래의 신규 동작·구조·일정·수치는 **추정: 설계 제안 또는 검증 목표**이며, 구현 완료나 최종 판정을 뜻하지 않는다. 후속 peer/review는 별도로 필요하다.

## 1. 사용자 흐름과 기본값

### 1.1 첫 진입과 최소 입력

**추정: 첫 화면의 주 입력은 자연어 한 칸과 ‘내 이사 만들기’ 버튼 하나다.** 업체명·예산·정확한 주소·이삿날을 필수로 요구하지 않는다.

예시 입력:

> 원룸, 출발 3층 엘리베이터 없음. 침대와 책장 옮겨요. 도착지는 아직 몰라요.

두 가지 진입 경로를 제공한다.

| 경로 | 사용자 행동 | 홈 생성까지의 부담 |
|---|---|---|
| 한 줄 입력 | 문장 입력 → 만들기 → 해석 요약 확인 | **추정: 문장 한 줄 + 버튼 2회** |
| 클릭 입력 | 원룸·투룸·기타·모름 중 선택 → 만들기 | **추정: 버튼 2회**. 나머지는 미확인으로 시작 |

‘원룸’을 골라도 침대·냉장고 등을 실제 소유한 짐으로 등록하지 않는다. 집 유형별 표준 짐 목록은 확보되지 않았다. 근거: `runs/out/b008-data.sol.md:173`, `:176`.

**추정: 기본값은 다음과 같다.**

- 업체: 선택 안 함.
- 날짜·지역·층수: `null`.
- 엘리베이터·주차·장비 필요 여부: `모름`.
- 짐 소유·운송 여부·수량: 확인 전에는 미확인.
- 선택 가능한 가구 후보: ‘확인용 예시’로 접어 둠. 기본 미선택.
- 견적·계약서·보험 증빙: 아직 받지 않음.
- 에이전트: 모두 켜짐. 해당 단계가 오기 전에는 대기.
- 외부 발송·계약·송금: 자동 실행 없음.

현재 코드에도 현장 조건의 `모름`과 빈 짐 목록이 있다. 다만 `Item.count`는 필수 숫자이므로, 수량 미확인을 표현하도록 확장이 필요하다. 근거: `web/src/lib/types.ts:23`, `web/src/lib/store.ts:25`.

### 1.2 단계별 흐름

| 단계 | 사용자가 하는 일 | 자동으로 제공하는 것·기본값 |
|---|---|---|
| 조건 입력 | 한 줄 작성 또는 집 유형 선택 | 문장에서 명시한 조건만 추출. 빠진 값은 모름 |
| 해석 확인 | 요약을 읽고 확인. 필요하면 수정 | 원문과 추출값을 함께 표시. ‘침대’만 있으면 수량은 모름 |
| 맞춤 홈 생성 | 바로 확인 | 조건 요약, 이삿짐 장면, 준비할 서류, 다음 행동 한 개 |
| 짐·조건 보완 | 아는 항목만 수정 | 관련 질문만 제시. 모든 칸을 채우도록 막지 않음 |
| 견적 받기 | 공통 요청문 복사, 직접 업체 탐색·발송 | 동일 조건의 견적 요청 초안. 미확인 조건도 함께 전달 |
| 여러 견적 비교 | 받은 견적을 건별로 붙여넣고 추출값 검토 | 같은 조건의 기재 내용·총액·별도 비용·증빙을 나란히 표시 |
| 업체 고르기 | 비교 근거를 보고 후보 선택 | 선택 이유·남은 확인 사항을 표시. 자동 계약 없음 |
| 계약 서류 점검 | 계약서 글 붙여넣기, 변경 사항 확인 | 견적·답변·계약서 간 누락과 상충 후보 |
| 이삿날 | 출발·인도 사실을 직접 기록 | 확인한 짐 체크, 관련 문서·증빙 바로 보기 |
| 사고 대응 | 사실·시각 입력, 증빙 연결 | 사건 경과와 업체에 요청할 문서 초안 |

견적 요청·허가·보험·상세계약 확인은 조사 자료의 권고를 따른다. 근거: `runs/out/b008-data.sol.md:51`, `:55`, `:64`, `:117`, `:119`.

### 1.3 선택 부담을 줄이는 장치

**추정: 사용자의 결정이 필요한 곳과 단순 편집을 분리한다.**

1. 홈에서는 ‘지금 할 일’ 하나만 크게 보여 준다. 나머지는 ‘나중에’.
2. 모르는 조건이 있어도 홈·요청문을 생성한다. 미확인 값은 누락시키지 않고 문구에 남긴다.
3. 조건은 홈 상단의 요약에서 언제든 수정한다. 처음부터 다시 입력하지 않는다.
4. 업체 문의는 관련 미확인 항목을 기본 포함한다. 사용자가 원하면 제외한다.
5. 답변에 따른 상태 변경 후보는 기본 미선택을 유지한다. 원문을 보고 승인한다.
6. 추천을 보기 전에 가중치·예산·선호도 설문을 요구하지 않는다.
7. 업체 이름이 없는 견적은 ‘견적 1’처럼 문서 식별자로 표시한다. 실제 업체명처럼 만들지 않는다.

현재 문의 항목 기본 포함과 답변 후보 개별 승인은 재사용할 수 있다. 근거: `web/src/components/InquiryPanel.tsx:19`, `:30`, `:155`.

### 1.4 업체를 고르는 기능의 범위

**추정: ‘업체 발견’과 ‘받은 견적 비교’를 이어 주되, 검증되지 않은 업체 목록을 채워 넣지 않는다.**

- 처음에는 빈 업체 화면에서 동일 조건 요청문과 허가 확인 경로를 제공한다.
- 서울 업체 데이터가 없으면 ‘이 지역 자동 후보 목록 미연결’로 표시한다.
- 사용자가 가져온 업체·견적을 비교의 중심으로 삼는다.
- 성남·김해 공개 목록을 추후 가져올 경우 지역·기준일·출처·이용 조건을 표시한다. 목록 등재만으로 현재 허가·보험·서비스 가능 지역을 확정하지 않는다.
- 비교표는 허가 증빙, 보험 범위, 조건 일치, 총액·별도 비용, 답변·계약 반영 여부를 보여 준다.
- 확인 자료가 충분하면 ‘현재 자료에서 우선 검토할 후보’와 이유를 제시한다. 자료가 부족하거나 우열이 갈리면 복수 후보와 보류 이유를 표시한다.
- 평점·종합점수·시장 최저가·자동 선정은 제공하지 않는다.

서울 전체 실시간 API와 업체 평점 근거는 `unknown`이며, 확인된 지역 목록도 연간 갱신 자료다. 근거: `runs/out/b008-data.sol.md:72`, `:74`, `:82`, `:84`, `:95`.

### 2.2 실행 순서와 병렬 여부

**추정: 실행 흐름은 다음과 같다.**

```text
조건 해석 → 사용자 확인
                 ├→ 짐 확인 ─────┐
                 └→ 현장 확인 ───┴→ 맞춤 홈·공통 견적 요청문

견적 읽기 1 → 견적 읽기 2 → … → 업체 대조
                                      ↓
                            문의·답변 점검 → 사용자 승인
                                      ↓
                            업체 선택 → 계약 문서 해석
                                      ↓
                            서류 점검 → 이삿날·사고 기록
```

- 짐 확인·현장 확인 등 서로 독립적인 규칙 작업은 병렬 실행할 수 있다.
- **모든 LLM 요청은 서버의 공통 GPU 대기열에서 한 번에 하나씩 실행한다.**
- 여러 업체 견적은 Ax4가 연속 처리한다. Qwen과 견적마다 번갈아 호출하지 않는다.
- 사건 정리는 사고 입력이 있을 때만 실행한다.
- 대기 중인 역할은 ‘실행 대기’로 표시한다. 가짜 작업 애니메이션을 켜지 않는다.

현재 Ollama 클라이언트는 직전 모델을 추적하지만, 공통 실행 대기열은 없다. 근거: `web/src/lib/ollama.ts:14`, `:53`.

### 2.3 토글의 실제 의미

**추정: 토글은 표시와 실행 모두에 적용한다.**

- 꺼진 역할의 대기 작업은 취소한다.
- 실행 중이면 취소를 요청하고, 취소 이후 도착한 결과는 버전·취소 토큰으로 반영을 막는다.
- 기존 결과는 지우지 않고 ‘이전 실행 결과 · 현재 꺼짐’을 표시한다.
- 입력 변경 뒤 재검증하지 못한 결과는 ‘갱신 필요’로 바꾼다.
- 의존 역할은 ‘대기: 견적 읽기 꺼짐’처럼 이유를 표시한다.
- 규칙 역할을 꺼도 원문 검증·승인 검사·숫자 생성 차단은 유지한다. 이 검증기는 토글 가능한 에이전트 밖의 필수 처리다.
- 전체 진행을 꺼도 기존 자료 열람과 수동 입력은 가능하다.

### 2.4 사람 승인이 필요한 지점

**추정: 사람 승인은 다음 네 종류에 한정한다.**

1. 자연어 해석 결과를 자신의 조건으로 확정할 때.
2. AI가 낸 답변 반영·계약 해석 후보를 채택할 때.
3. 업체를 선택하거나 선택을 바꿀 때.
4. 외부 전달·계약·송금·사고 사실확인 문서를 실제로 사용할 때.

조회·규칙 점검·초안 작성에는 추가 승인을 요구하지 않는다. 복사는 발송으로 처리하지 않는다. 기존 정책 근거: `web/src/lib/types.ts:50`, `web/src/components/InquiryPanel.tsx:110`.

### 2.5 로컬 GPU 시간 예산

측정 근거는 사용자가 제공한 Qwen 웜 약 6초/턴, Ax4 읽기 7~13초, 모델 전환 시 콜드 37~112초다. 기존 코드에도 콜드 관측과 모델 교대 제약이 기록되어 있다. `web/src/lib/ollama.ts:10`. v0.2의 읽기·답변 점검 관측은 `decisions/D005-이사-지킴이-대시보드.md:17`에 있다.

**추정: 신규 역할은 길이·작업이 달라 아래 값은 계획용 예산이며, 실제 지연은 재측정해야 한다.**

| 작업 | 계획 호출량 | 웜 실행 예산 |
|---|---:|---:|
| 조건 해석 | Qwen 1턴 | 6초 |
| 견적 2건 읽기 | Ax4 2회 | 14~26초 |
| 답변 점검 1건 | Qwen 최대 4턴 | 24초 |
| 계약 문구 해석 | Qwen 1턴 | 6초 |
| 사고 메모 정리 | Qwen 1턴 | 6초 |
| 규칙·직렬화·화면 반영 | 별도 처리 | 총 3초 목표 |
| **전체** | Qwen 7턴 + Ax4 2회 | **59~71초** |

현재 답변 점검은 최대 6턴·도구 8회다. 4턴 예산을 적용하려면 실제 상한을 변경하고 재평가해야 한다. 상한 도달은 정상 완료와 구분한다. 근거: `web/src/lib/agent.ts:8`, `:160`, `:184`.

**추정: Qwen으로 시작해 Ax4 견적을 묶어 읽고 다시 Qwen으로 돌아오면 모델 전환은 2회다.** 계획상 로딩 비용을 보수적으로 별도 더하면:

- 시작 모델 웜: `59~71 + 2×(37~112)` = **133~295초**.
- 시작도 콜드: 여기에 37~112초 추가 = **170~407초**.
- 콜드 관측값에는 추론 시간이 일부 포함됐을 수 있어, 이는 보수적인 예산이다. 정확한 분해는 `unknown`.

따라서 전체 신규 자료 처리를 3분 이내라고 약속하지 않는다. 시연 시간은 7절처럼 별도로 설계한다.

표준약관 조항은 **어떤 항목을 살펴볼지의 근거**다. 특정 업체의 포함 약속·허가·보험가입 사실을 입증하는 근거와 구분한다.

예를 들어 ‘계단 비용 확인 필요’는 다음 두 경로로 설명한다.

```text
출발지 3층·엘리베이터 없음 → 계단 작업 확인 질문
견적 원문 “당일 현장 협의” → 조건 모호
참고 조항 → 작업조건·비용을 확인하는 점검 기준
```

### 4.2 상태와 값의 출처

**추정: 상태는 개별 주장·필드에 붙이며 문서 전체에 일괄 적용하지 않는다.**

| 상태 | 의미 |
|---|---|
| 확인됨 | 해당 출처에서 해당 내용을 확인함. 사실의 범위·확인 주체를 병기 |
| 미확인 | 자료가 없거나 아직 확인하지 않음 |
| 모호 | 조건부 표현, 해석 불명확 또는 상충 자료가 있음 |
| 판독불가 | 자료는 있으나 텍스트 손상·파싱 실패 등으로 읽지 못함 |

- ‘문서에 명시됨’, ‘사용자 확인’, ‘기관 조회 결과’는 출처 유형으로 따로 표시한다.
- 업체 답변에 ‘포함’이라고 적혔다는 사실이 실제 이행 보증으로 확장되지 않게 한다.
- 비용 처리는 상태와 별개로 `총액 포함 / 별도 / 미확인 / 해당 없음`을 유지한다.
- 실행 상태 `꺼짐·대기·오류`와 자료 상태를 섞지 않는다.
- 자료가 아예 없는 경우를 판독불가로 표시하지 않는다.

현재 비용과 기재 상태의 분리는 재사용할 수 있다. 반면 총액이 `null`이면 판독불가 카드를 만드는 처리는 미기재와 판독 실패를 나누도록 수정해야 한다. 근거: `web/src/lib/types.ts:30`, `web/src/lib/rules.ts:134`.

### 7.2 3분 시연 시나리오

**추정: 시연은 ‘가상 사례·견적 사전 처리’임을 시작부터 표시한다.** 업체는 ‘가상 견적 A/B’로 표기하고 실제 업체 이름처럼 제시하지 않는다. 사전 처리한 견적은 동결된 시연 조건에만 연결한다. 조건이 달라지면 재점검 필요로 표시한다.

| 시간 | 시연 내용 | 관객이 확인할 점 |
|---|---|---|
| 0:00~0:25 | “원룸, 3층 엘리베이터 없음, 침대와 책장…” 입력 → 해석 확인 | 문장에 없는 수량·가격은 채우지 않음 |
| 0:25~0:45 | 맞춤 홈 생성, 사람이 짐·문서 도형을 이동 | 결과 이벤트와 장면·표가 동기화됨 |
| 0:45~1:10 | 사전 처리한 가상 견적 A/B 연결 | 동일 조건 비교, 별도 비용·증빙 차이 표시 |
| 1:10~1:45 | Qwen으로 업체 답변 실시간 점검 | 명시·조건부·미답 분리, 원문 근거와 후보 표시 |
| 1:45~2:05 | 조건부 답변 후보 확인, 허용 후보만 승인 | 자동 확정하지 않고 남은 질문 유지 |
| 2:05~2:25 | 후보 업체 선택, 계약서 누락과 근거 사슬 열기 | 업체 선택 이유와 서류 확인 연결 |
| 2:25~2:45 | 역할 하나 끄고 관련 입력 수정 | 꺼짐·갱신 필요·의존 대기가 실제로 바뀜 |
| 2:45~3:00 | 사고 메모·증빙 화면, 움직임 끄기 | 사실 기록 중심 대응과 접근성 |

**추정: 이 시연의 신규 LLM 예산은 조건 해석 6초 + 답변 점검 최대 24초 = 약 30초**, 규칙·화면 반영 여유를 포함해 약 33초다. 모델은 Qwen을 미리 웜 상태로 준비한다. 계약·사고 해석을 추가로 실시간 실행하면 약 6~12초를 더 배정해야 한다.

연결 실패 시에는 ‘라이브 실행 실패’를 표시하고 수동 점검 또는 표시된 기록 재생으로 전환한다. **새 견적의 읽기·모델 전환을 포함한 전체 처리 시간은 별도 측정값으로 제시한다.**
