## 0. 문제 정의와 먼저 알려야 할 것

**서비스가 푸는 문제(변하지 않음, D003·D005)**: 소규모 이사 소비자가 계약금을 보내기 전에 견적의 빈칸 — 포함 여부 미확인·조건 모호·추가비 조항 — 을 몰라서 이삿날 "이건 추가요"를 당한다. v0.3의 모든 기능·화면·에이전트는 **"계약금 송금 전에 물어야 할 질문을 빠짐없이 뽑고, 확인 안 된 것을 확인됨으로 잘못 바꾸지 않는다"** 에 기여해야 하고, 기여하지 않으면 뺐다(§3). 에이전트 장면은 독립 기능이 아니라 이 점검 과정을 눈에 보이게 하는 표현이다(§5-3).

1. **"서류·문서 산정"은 '서류 목록·확인 항목 산정'으로만 구현한다.** 짐 ㎥·톤수·인원·가격 산정표는 근거가 `unknown`이다(`b008-data.sol.md` §1·§4·§5). 홈 KPI와 장면 어디에도 예상 금액·톤수·적재율(%)을 넣지 않는다. 트럭 옆 막대는 적재율이 아니라 **"확인 완료 N/M"** 이다. "산정 불가: 근거 없음" 칸을 의도적으로 보여 준다(심사에서 정직성이 강점인지는 Astra 검토 대상).
2. **주소 '구' 입력은 선택 칩 1개로만 둔다.** 구 단위 허가 업체 목록은 현재 **관악구만** 확인됐다(의장 확인: 공공데이터포털 15080952, 아래 §2-2 도우미). 강남·서초·동작·성동은 검색 결과만 있고 미열람이다. 칩은 `관악구 / 그 외 / 모름`이고 기본 `모름`, 관악구일 때만 후보 목록을 켠다. 그 외 지역은 "이 지역 목록은 아직 없음"이며 나머지 기능은 그대로 쓴다.
3. **팀 색은 팔레트 A에 2개뿐이다.** 장면용 옷 색은 `#2F6DB5`, `#B84A18` 둘뿐이다(`b008-palette.sonnet.md` A "2D 장면"). 세 팀 구분은 옷 색 2개 + 모자 줄 수 + 이름표로 하고, 세 번째 색은 필요하면 사용자에게 hex를 보고하고 대비 검사 후 쓴다.
4. **로컬 모델 2개 교대 비용이 시간 예산을 지배한다.** 콜드 37~112초(`web/src/lib/ollama.ts:10-12` 주석 "실측", `COLD_TIMEOUT_MS=180_000`). 모델 사용 순서를 고정하는 것이 핵심 제약이다(§2-6).
5. **해커톤 사전 구현 허용 여부는 `unknown`.** 권장 항목은 "구현 계획"이고 본선은 "하루에 구현·시연"이라고만 돼 있다(`team/prompts/_context.md:7`). §6은 사전 구현과 당일 최소 범위를 나눠 적었다.
6. **표준약관 수치 정정 반영**: 제9조 제3항(사업자 귀책 인수 2시간 이상 지연) = 6배액, 제15조(고객 귀책 인수 지체) 한도 2배로 서로 다른 조항이다(의장이 정정; 이전 "2배 vs 6배 상충"은 조항을 혼동한 것). 그래도 배상·해제 금액 계산기는 만들지 않는다 — 추가요금 분쟁을 계약 전에 줄이는 데 직접 기여하지 않고, 공정위 원본 최신판 대조가 끝나지 않았다(`b008-data.sol.md` §3).
7. **TRITON에서 가져오는 것은 4가지뿐이다**: 디자인 체계(셸·토큰 구조), 왼쪽 레일(`nav.ts` 데이터 구조), 자동 진행 엔진(`useAutoReveal`·`reveal.ts`), 근거 그래프·온톨로지 구조(`evidenceLayout`·`graphModel`·`ontology.yaml`). **이삿짐 장면과 에이전트 캐릭터는 TRITON에 없던 새 아이디어이고 처음부터 SVG로 새로 그린다.** TRITON 법정 장면(PNG 기반)·미사용 `Person.tsx`·`Scale2d.tsx`는 이식하지 않는다(`b008-triton.sonnet.md` §0).

## 2. 에이전트 조직표 (1 + 3 x 3)

### 2-1. 한눈에

LLM은 **3명**(조건 해석관, 문서 읽기관, 답변 점검관), 규칙(결정적 코드)은 **7명**(지휘관 포함). 10명 전부 LLM이면 직렬 GPU에서 수 분이 걸리고, 근거 없는 숫자 위험도 커진다. 화면에는 에이전트마다 `LLM` / `규칙` 태그를 항상 표시한다(정직성).

### 2-2. 에이전트별 명세

공통: 모든 에이전트는 외부로 보내는 도구(웹 검색, 전송)가 없다. 상태를 바꾸는 쓰기는 지휘관이 승인 단계(§2-7)를 거쳐서만 한다.

**0. 지휘관 (규칙)**
- 하는 일: 단계(1 조건 → 2 견적 → 3 선택 후 → 4 계약·이삿날)를 진행하고, 켜진 에이전트만 순서대로 호출하고, 결과를 "장면 이벤트"로 바꿔 장면·서술 카드·로그에 흘린다. LLM 호출은 **뮤텍스 1개**로 직렬화한다.
- 입력: 사용자 입력·에이전트 결과·켜짐 상태. 출력: 실행 계획, 장면 이벤트 큐, "지금 일어나는 일" 문장(템플릿 — TRITON `narrate.ts` 방식, 상태에서 `{title, detail}` 생성).
- 도구: 없음(다른 에이전트 함수 호출만). 꺼짐: **꺼지지 않는다**(레일에서 잠금 표시). 다른 9명 상태 표시와 의존 경고를 책임진다.
- 숫자 방지: 자기가 숫자를 만들지 않는다. 화면 숫자는 다른 에이전트 결과의 `length`(건수)이거나 사용자 입력뿐이다.

**1. 조건 해석관 (LLM, `ax4-light`)**
- 하는 일: 한 문장 → `{집 유형, 출발/도착 층, 엘리베이터, 사다리차 필요, 언급한 짐 이름·수량}`. 문장에 없으면 `null`/`모름`.
- 입력: 사용자 문장(≤300자). 출력: v0.2 `Conditions` + `Item[]` 초안. 도구: `chatJSON` + 스키마 하나(도구 호출 아님).
- 실행: 가장 먼저(단계 1), 다른 LLM과 병렬 불가. 시간: 웜 7~13초(추정: 읽기관과 같은 모델·비슷한 크기, 직접 측정은 없음).
- 꺼짐: 문장 입력칸이 비활성화되고 "조건 해석관 꺼짐 — 칩으로 입력" 표시. 칩 입력은 항상 작동(대체 경로).
- 숫자 방지: ① 스키마의 숫자 칸은 전부 nullable ② **검증 함수**(신규 `intake.ts`, `verifyDraft` 방식): 층수는 문장에 해당 숫자가 있어야, 짐 이름은 문장에 부분 문자열로 있어야, 수량은 `N개/대` 표기가 있어야 통과 ③ 통과 못 한 값은 버리고 화면에 "읽지 못함 n개" 표시 ④ 승인: 칩 확인 화면에서 사용자가 고침.

**2. 짐 점검표관 (규칙)**
- 하는 일: 집 유형 → **이름만 있는 확인용 후보 목록**(냉장고·세탁기·침대 …, 수량·부피·무게 없음). 문장에서 사용자가 말한 짐은 `직접`으로 미리 표시.
- 입력: 집 유형·언급한 짐. 출력: `Item[]`(후보, `move=false`, 상태 `모름`). 도구: 고정 이름표 `COMMON_ITEMS`.
- 실행: 조건 해석관 뒤, 서류 안내관과 **병렬**(CPU 즉시).
- 꺼짐: 짐 패널에 "점검표 꺼짐 — 직접 추가만 가능" 표시, 장면 출발 집은 빈 마당(상자 없음).
- 숫자 방지: 이름만 낸다. 라벨은 항상 **"확인용 후보 — 표준 목록 근거 없음"**(Sol §5 권고). 후보를 확정 물량으로 합산하지 않음.

**3. 서류 안내관 (규칙)**
- 하는 일: "받아야 할 서류" 목록을 2묶음으로 낸다 — 계약 전(견적서: 제4조 기재 항목), 계약 때(계약서: 제5조 제2항, 약관 설명·사본 제5조 제1항). 사고증명서(제19조)는 계약 후 피해 구제 영역이라 목록에서 뺐다(§3). 각 항목에 조항 id와 출처.
- 입력: 없음(고정 표 + 업체 선택 여부). 출력: `DocItem[]`(상태 `받음/아직`). 도구: `references.ts` 확장 표.
- 실행: 조건 해석관 뒤 병렬. 시간 <0.1초(추정).
- 꺼짐: 서류 패널에 "서류 안내관 꺼짐" 표시, 도착 집 앞 서류철이 비어 있고 "꺼짐" 라벨.
- 숫자 방지: 항목·조항 번호는 `b008-data.sol.md` §3 표에서만. 고객 **주민등록번호를 입력 항목으로 넣지 않는다**(생활법령 629와 666 상충, §3 "주의할 원문 차이"). 라벨: "확인 판본 제10035호(2014-09-19 개정), 최신 개정 여부 추가 확인 필요".

**4. 문서 읽기관 (LLM, `ax4-light`)**
- 하는 일: 붙여넣은 견적서(또는 계약서) 글 → 항목(`QuoteDraft` 스키마, 계약서는 별도 스키마: 계약금·잔액·운송상 주의사항·고객 요청사항·약관 사본 여부). v0.2 그대로.
- 입력: 글(10~5,000자, `route.ts` 제한). 출력: 초안 + 걷어낸 목록 `dropped`. 도구: `chatJSON`.
- 실행: 견적 1건당 1회, 직렬. 시간: 7~13초/건(D005 실측 "읽기 7~13초").
- 꺼짐: 붙여넣기 칸에 "읽기관 꺼짐 — 총액·차량·인원·사다리차를 직접 입력" 폼으로 대체. 대조·비교는 직접 입력값으로 계속 동작.
- 숫자 방지: **v0.2 `verifyDraft` 그대로** — 총액·계약금은 원문 금액 표기(350,000원/35만/3만5천 등)에 있어야 하고(`verify.ts` `amountsIn`), 인원은 `N명|인`이 원문에 있어야 하며, 사다리차 `포함/별도`는 원문에 "사다리"가 있을 때만 인정. 걷어낸 값은 사용자에게 보여 준다.

**5. 견적 대조관 (규칙)**
- 하는 일: 사용자 짐·조건 ↔ 견적 항목을 비교해 확인 카드 생성(품목·작업조건·추가비 3규칙, 4상태). 견적별 1세트.
- 입력: `Item[]`, `QuoteDraft`, `Conditions`. 출력: `Card[]`. 도구: `rules.ts` `compare`.
- 실행: 문서 읽기관 결과가 나올 때마다 즉시, **견적 간 병렬 가능**. <0.1초.
- 꺼짐: 대조표 패널에 "견적 대조관 꺼짐 — 읽은 값만 표시", 장면에서 트럭의 상자에 상태 기호 없음("대조 안 됨" 꼬리표), 문의·답변 단계는 "카드 없음"으로 비활성.
- 숫자 방지: 규칙이 만드는 문장 안의 숫자는 사용자 입력 수량·견적 원문 발췌뿐(v0.2 구조). 판정에 LLM 없음.

**6. 업체 고르기 도우미 (규칙)**
- 하는 일: 견적 2~3건을 **같은 조건 비교표**로 만든다. 열: 총액(읽은 값 그대로), 차량·인원(읽은 값), 사다리차, 짐 후보 확인 N/M, 추가비 문구 유무, 허가 증빙(`확인/미확인`), 보험 증빙(`확인/미확인/범위 확인 필요`). 정렬 기본값은 **"확인이 남은 항목이 적은 순"**이며 점수·별점·순위 숫자는 없다.
- 입력: 카드 세트들, 사용자가 체크한 증빙 상태, **관악구 허가 업체 목록 스냅샷**(칩이 관악구일 때만). 출력: `CompareTable`, "먼저 확인할 것 3줄", 업체 후보 목록, 허가 목록 대조 칩. 도구: 없음. 근거: 한국소비자원 허가·보험·방문견적 권고(`b008-data.sol.md` §2 [KCA-C]).
- **관악구 허가 업체 목록 사용(의장 확인)**: 공공데이터포털 '서울특별시 관악구_화물자동차운송주선사업허가업체현황_20260424' https://www.data.go.kr/data/15080952/fileData.do — CSV 39행, 항목 업체명·인허가일자·영업상태명·소재지주소·위도·경도·구분·전화번호·데이터기준일자, 이용허락범위 제한 없음·무료, 등록 2026-05-04, 연간 갱신, Open API는 활용신청 필요. 강남(15081027)·서초(15081137)·동작(15080928)·성동(15081008)도 같은 종류 파일이 있다는 검색 결과가 있으나 **미열람**이라 지원 지역에 넣지 않는다. 두 가지 용도뿐이다: ① **견적 받을 후보를 고르는 출발점** — 목록을 "후보 명단(정렬 없음, 영업상태·인허가일자·데이터 기준일 표시)"으로 보여 주고 사용자가 직접 골라 견적을 요청한다. 추천·순위·평점은 없다 ② **받은 견적서의 업체명이 목록에 있는지 대조** — 있으면 "관악구 목록에 있음(영업상태·인허가일·기준일)", 없으면 "목록에서 찾지 못함 — **무허가라는 뜻이 아닙니다**(연간 갱신, 관할 외 업체 가능). 허가증 사본을 요청하세요". **전화번호 열은 개인 휴대폰일 수 있다는 유의사항이 있어 가져오지 않는다**(화면·저장소에 넣지 않음; 가져오기 스크립트가 해당 열을 버림). 업체명 일치는 공백·`(주)` 정규화 후 완전 일치만 인정하고 비슷한 이름은 "비슷한 이름이 있음, 직접 확인"으로만 표시한다(추정:).
- 실행: 모든 견적 읽기·대조가 끝난 뒤 1회. <0.1초.
- 꺼짐: 비교 패널이 "업체 고르기 도우미 꺼짐 — 견적별 카드만 표시"로 바뀌고 비교표 자리는 빈 칸.
- 숫자 방지: 가격 점수·평판 없음(Sol §2: 평가 데이터 unknown). 표의 모든 칸은 "읽은 값" 또는 "건수"뿐. 업체 이름은 사용자가 붙인 글에서만 나온다 — 업체 목록을 앱이 만들지 않는다. 허가는 "증빙 확인했음"을 사용자가 눌러야 표시하고, 조회 API 연동으로 표현하지 않는다(엔드포인트 `unknown`; 위 CSV는 기준일이 있는 스냅샷일 뿐 실시간 조회가 아니다).

**7. 문의 작성관 (규칙)**
- 하는 일: 선택한 업체의 `확인 필요` 카드(`status != 명시됨`)에서 질문을 모아 업체에 보낼 글을 만든다. 질문은 카드의 `ask` 한 문장(v0.2).
- 입력: `Card[]`. 출력: 복사용 글, 문의 상태. 꺼짐: 문의 패널 "문의 작성관 꺼짐 — 카드의 질문을 직접 복사" (질문 자체는 카드에 남음).
- 숫자 방지: 질문 문장은 `rules.ts` 템플릿(카드 `ask`)만 쓴다. LLM이 질문을 쓰지 않는다.

**8. 답변 점검관 (LLM, `qwen3:4b-instruct`)**
- 하는 일: 업체 답변을 읽고 확인이 남은 카드에 대한 갱신 **후보**를 낸다(`explicit_answer/conditional_answer/conflicting/unanswered`). v0.2 코드 그대로(`agent.ts`: `MAX_TOOL_CALLS=8`, `MAX_TURNS=6`).
- 도구: `get_open_cards`, `find_in_reply`, `propose_updates`, `finish`(외부 전송 도구 없음).
- 실행: 업체 선택 이후, 답변 1건당 1회. 시간 9~11초/건(D005 실측 "점검 9~11초").
- 꺼짐: 답변 칸에 "점검관 꺼짐 — 카드별로 직접 `답변 반영`을 누르세요". 수동 승인 UI는 v0.2에 이미 있음.
- 숫자 방지: **코드가 후보를 거절**(quote가 답변 원문에 그대로 있어야, 카드 낱말이 들어 있어야, `NOT_PLAIN_YES`(`agent.ts:45`) 표현이 있으면 `명시됨` 불가). 후보는 사용자 승인 뒤에만 반영, 입력이 바뀌면 승인 무효(`store.ts` `sigOf`).

**9. 계약 점검관 (규칙)**
- 하는 일: (a) 문서 읽기관이 읽은 계약서 항목에서 제5조 제2항 항목 누락 점검 (b) 계약금이 총액의 10%를 넘는지 알림(제6조 "합계액의 10% 청구 가능") (c) 이삿날 증거 남기기 체크리스트(현장 피해 사실확인서 요청·사진, KCA-C).
- 입력: 계약서 초안, 총액·계약금(읽은 값). 출력: 점검 카드. 도구: 고정 표.
- 꺼짐: "계약·서류" 화면과 "이삿날·사고" 화면에 "안내관 꺼짐" 배너, 장면의 도착 집 문이 잠긴 상태로 표시.
- 숫자 방지: 계약금 비율 계산은 **사용자 입력 두 숫자의 나눗셈**뿐이고 조항 숫자(10%)는 표에서만 온다. 해제·지연 배상 금액 계산은 하지 않는다(§0-6).
- 조항 표시 라벨은 항상 "최신 개정 여부 확인 필요"(공정위 원본 대조 미완 — `b008-data.sol.md` §3).

### 2-3. 실행 순서와 병렬

```
지휘관(plan)
  단계1  조건 해석관(LLM, 직렬 슬롯) ─┬─ 짐 점검표관(규칙) ┐ 병렬
                                      └─ 서류 안내관(규칙) ┘
  단계2  [견적 i마다] 문서 읽기관(LLM, 직렬) → 견적 대조관(규칙)   ← 규칙은 다음 견적 읽는 동안 즉시 실행
         → (모든 견적 완료) 업체 고르기 도우미(규칙)
  단계3  (업체 선택 후) 문의 작성관(규칙) → [사용자: 보냄·답변 붙임] → 답변 점검관(LLM)
  단계4  문서 읽기관(계약서) → 계약 점검관(규칙)
```
- LLM 직렬: 조건 해석관 → 문서 읽기관 x N → 답변 점검관 x M(+ 계약서 읽기 1회). 규칙 에이전트는 서로 병렬이며 LLM이 도는 동안 같이 실행된다.
- **모델 교대 최소화**: `ax4-light` 호출을 먼저 모두 끝내고(조건·견적·계약서) `qwen3`는 마지막(답변 점검)에만 쓴다. 사용자가 단계3으로 가기 전(업체 고르는 몇 초~수십 초)에 `qwen3`를 **미리 올린다**(빈 요청으로 로드; 추정: 이때 `ax4-light`가 내려가 교대 1회가 사람 대기 시간에 숨음. Ollama가 두 모델을 동시에 올리는지는 `unknown`이므로 시연 전 실측 필요).

### 2-4. 켜짐/꺼짐 영향표

| 끈 에이전트 | 빠지는 것 | '꺼짐'이 보이는 화면 | 대체 경로 |
|---|---|---|---|
| 지휘관 | (끌 수 없음) | 레일에 자물쇠 | - |
| 조건 해석관 | 한 문장 → 조건 | 시작 화면 문장칸, 홈 조건 칩 헤더 | 칩 입력 |
| 짐 점검표관 | 확인용 후보 | 짐·조건, 무대(빈 마당) | 짐 직접 추가 |
| 서류 안내관 | 받을 서류 목록 | 홈 KPI '서류 N건' → `꺼짐`, 계약·서류 | 없음(표시만 비움) |
| 문서 읽기관 | 견적서·계약서 읽기 | 견적·업체(붙여넣기 칸) | 총액·차량·인원·사다리차 직접 입력 |
| 견적 대조관 | 확인 카드 | 견적·업체 대조표, 무대(상자 기호), 문의 | 읽은 값만 표시 |
| 업체 고르기 도우미 | 비교표·먼저 확인할 것 | 견적·업체(비교표 자리) | 견적별 카드 개별 열람 |
| 문의 작성관 | 문의 글 | 문의 패널 | 카드 질문 개별 복사 |
| 답변 점검관 | 자동 후보 | 문의 패널(답변 칸) | 카드별 수동 `답변 반영` |
| 계약 점검관 | 계약서 점검·이삿날 증거 체크 | 계약·서류, 이삿날, 무대(도착 집 문 잠김) | 없음 |

규칙: 꺼진 에이전트의 **이전 결과는 지우지 않고 숨긴다**(다시 켜면 즉시 복귀). 상류가 꺼지면 하류 에이전트 행에 "상류 꺼짐: 입력 없음"을 표시한다(예: 견적 대조관 켜짐 + 문서 읽기관 꺼짐 + 직접 입력도 없음). 상단바는 "에이전트 N/10 활성 · 작업 중 k"(TRITON `ConsoleShell.tsx:158-166` 배지 방식). 레일에서 끌 때 한 줄로 영향을 미리 보여 준다("끄면: 견적서 읽기가 직접 입력으로 바뀝니다").

### 2-5. 근거 없는 숫자 방지 장치 요약

| 장치 | 적용 |
|---|---|
| 스키마 nullable + 원문 대조 | 조건 해석관(신규), 문서 읽기관(`verifyDraft`) |
| 문장 템플릿만 사용 | 지휘관·문의 작성관·대조관(숫자는 입력·원문 발췌만) |
| 조항 문구는 코드 표에서만 | 서류 안내관·계약 점검관(모델은 조항을 쓰지 않음 — `references.ts` 헤더 주석) |
| 점수·순위·가격·톤수·㎥ 출력 자체가 없음 | 업체 고르기 도우미, 짐 점검표관 |
| 코드가 후보 거절, 사용자 승인 | 답변 점검관 |
| **자동 시험** | 모든 화면의 숫자 토큰을 수집해 (입력 / 원문 / 조항 표 / 건수) 중 하나로 추적되는지 검사하는 테스트(§7 기준 3) |

### 2-6. 시간 예산 (로컬 GPU 1대, LLM 직렬)

측정값: 읽기 7~13초/건, 점검 9~11초/건(D005 "검증" 줄), 콜드 37~112초(`ollama.ts` 주석). 조건 해석 7~13초는 **추정:**(직접 측정 없음). 규칙 에이전트 합계 <1초는 **추정:**.

| 시나리오 | 구성 | 최소(초) | 최대(초) | 비고 |
|---|---|---|---|---|
| 3분 시연(견적 2건, 답변 1건, 모델 선로딩 성공) | 조건 7~13 + 읽기 2x(7~13) + 점검 9~11 | 30 | 50 | 시연 직전 `ax4-light` 워밍업 필수 |
| 같은 시연, 선로딩 실패(교대 노출) | 위 + 콜드 37~112 | 67 | 162 | 최악이 3분을 거의 채움 → 시연은 선로딩 실패 대비 대체 흐름 필요 |
| 전체 사용(견적 3건, 계약서 1건, 답변 3건) | 조건 + 읽기 4회 + 점검 3회 + 교대 1회 | 7+28+27+37 = 99 | 13+52+33+112 = 210 | 사용자 체감은 단계별로 나뉘어 분산됨 |
| 규칙 8명만(Ollama 꺼짐) | LLM 0회 | <1 | <1 | 칩 입력 + 직접 입력으로 전 단계 완주(§7 기준 9) |

장면 재생은 이와 별개: 이벤트 1개당 1.2초(TRITON `lib/reveal.ts:6-18` 간격, `useAutoReveal`) x 이벤트 약 15~25개(추정:) = 18~30초. LLM 대기 시간과 **겹쳐서** 흐르며 건너뛰기 가능. 즉 LLM이 도는 동안 화면이 멈추지 않는다. 단, 규칙 결과를 1.2초 간격으로 보여 주는 것은 연출임을 화면 우상단 "재생 속도" 표기로 밝힌다.

### 2-7. 사람 승인이 필요한 지점 (TRITON `actions.autonomy` 대응)

`agents/ontology.yaml:103-106`의 `autonomy: ai | human_approval | human_only`를 되돌리기 쉬운 정도로 다시 쓴다.

| 단계 | 의미 | 예 | 승인 |
|---|---|---|---|
| L0 `ai` | 읽기·표시·목록 | 서류 목록, 짐 후보, 대조 카드 생성 | 없음 |
| L1 `ai` (되돌리기 쉬움) | 값 채우기 | 조건 칩 채움, 견적 초안 읽기 | 사용자는 고치기만(기본 통과) |
| L2 `human_approval` | 상태를 바꿈 | 답변 반영, 읽기 결과 수정 확정 | **버튼 승인 필수**(v0.2 유지) |
| L3 `human_only` | 외부 영향·돈·계약 | 문의 발송, 업체 선택, 계약 체결, 계약금 송금, 서류 `받았음` | **앱은 하지 않음** — 안내만, 사람이 직접 |

**⑤ 오른쪽 산정표·서류 점검표 동기화**

- 데이터 흐름: 에이전트 결과 → `SceneState`(순수 함수, 시험 가능) → 장면 이벤트 큐 → (a) 그림 이동 (b) 오른쪽 행 추가가 **같은 이벤트 id로 동시에** 일어난다. 그림과 표가 어긋날 수 없다.
- 오른쪽은 탭 3개: **산정표**(카드 행, ✓?△⌀ 칩 + 비용 칩), **업체에 물을 질문**(멈춘 상자의 `ask`, 복사 버튼, 배지 = 게시판 숫자), **서류 점검표**(받을 서류 칸, `받았음` 체크 → 서류 선반에 한 장 꽂힘).
- 상호 연결: 상자·표지를 누르면(또는 키보드로 선택하면) 해당 행이 강조되고 스크롤되며, 행을 누르면 상자가 깜빡인다. 상태 변화(승인)는 상자 이동 + 행 칩 변경 + 질문 목록에서 해당 질문이 "답변 반영"으로 이동이 한 번에 일어난다.
- 재생: `useAutoReveal`(1.2초 간격, 건너뛰기 40ms; `lib/reveal.ts:6-18`)을 React state로 옮겨 쓴다. LLM 결과는 도착 즉시 큐에 들어가고 규칙 결과는 1.2초 간격으로 풀어 보여 준다(연출 속도임을 "재생 속도" 표기로 밝히고 건너뛰기 제공).

**⑥ 동작 줄이기**

- `prefers-reduced-motion` 또는 사용자 토글 "장면 움직임 끄기": 이동·동작 애니메이션 없이 **최종 상태를 즉시 표시**하고, 변화는 서술 카드(`aria-live="polite"`)와 오른쪽 행으로만 전달한다. 정보 손실 없음(모든 상자 상태가 목록에도 있음).
- 화면 밖·탭 숨김일 때 애니메이션 정지. 반복 애니메이션은 작동 중 캐릭터에만, 동시 최대 4개. `transform`·`opacity`만 애니메이션.
- 상자·표지·캐릭터는 `role=button`, `tabIndex`, 한국어 `aria-label`("냉장고 1개, 트럭 앞에서 멈춤, 포함 여부 미확인, 질문 1건"), Enter/Space로 선택. 상태는 색+기호+글자 3중.
