## p.1 한눈에 보기 — 이사 지킴이

**계약금을 보내기 전에, 견적의 빈칸을 업체에 물어볼 질문으로 바꿉니다.**

팀명: __________　구성원: __________

**이사 지킴이**  
이사 조건과 받은 견적을 대조해, 확인 질문·업체 답변·원문 근거를 연결하는 계약 전 점검 플랫폼.

> **가상 사용 장면**  
> 관악구에서 자취방을 옮기는 학생이 견적을 받았다. “기본 작업 포함”이라고 적혀 있지만, 엘리베이터 없는 집에서 짐을 내리는 작업까지 포함하는지는 알 수 없다. 계약금을 보내기 전, 무엇부터 물어봐야 할까?

한국소비자원이 분석한 소규모 이사 피해구제 신청에서 20~30대가 **65.1%**를 차지했다.[1] 피해 유형에는 짐의 양·건물 구조 등을 이유로 한 추가비용 요구와, 비용 협의가 어긋난 뒤의 계약 이행 거부가 포함된다.[1]

이사 지킴이는 이 상황에서 **“괜찮은 견적인가?”라는 막연한 걱정을 “이 작업이 포함됐는가?”라는 구체적인 확인으로 바꾼다.**

[표 1: 서비스 한눈에 보기 — 열 구성: 항목 / 제안 내용 / 구현·계획·가설 구분]

| 항목 | 제안 내용 | 구분 |
|---|---|---|
| 문제·사용자 | 소규모 이사를 준비하는 청년이 자신의 짐·작업조건과 견적의 포함 범위를 확인하기 어려움 | 공공 피해 자료에 근거한 문제 설정 |
| 해결 | 조건 정리 → 견적 대조 → 업체별 문의 → 답변 점검 → 공통 항목 비교 | 핵심 흐름 구현됨 |
| AI 역할 | 자연어 조건·견적·답변을 읽어 사용자가 검토할 초안 생성 | 구현됨 |
| 차별성 | 이미 받은 외부 견적에서 출발해 확인 질문과 원문 근거까지 연결 | 구현됨 / 경쟁 우위는 검증할 가설 |
| 구현 준비 | 실제 모델을 연결한 웹 흐름 실행 및 오류 수정 기록 확보 | 구현됨, D006 기준 |
| 기대 가치·수익 | 확인 없이 송금하는 선택 감소 / 소비자 무료·기관 유료 제공 | 검증할 가설 / 사업모델 후보 |

[그림 0: 계약금 송금 전의 질문 — 가상 사용자의 견적 문구 “기본 작업 포함” 옆에 “계단 운반도 포함인가요?”라는 확인 질문을 배치하고, 이삿날 추가비용 협의로 이어질 수 있는 지점을 점선으로 연결. 실제 인터뷰·피해 사례로 표시하지 않음]

*통계 범위: 소규모 이사 피해구제 신청 분석이며 전체 청년의 피해율이 아니다.[1] 구현 상태는 [D006 구현 기록][D006] 기준이다.*

## p.2 왜 지금·어떤 문제인가 — 이사비 부담과 계약의 불확실성

**이사비를 마련하는 일과, 그 돈에 어떤 작업이 포함되는지 확인하는 일은 함께 필요합니다.**

한국소비자원의 이사서비스 피해구제 신청은 2023년 **603건**[1], 2024년 **785건**[1], 2025년 **961건**[1]이었다. 소비자원은 비대면 소규모 이사 계약에서 짐의 양이나 건물 구조를 이유로 추가비용을 요구하는 문제를 설명한다.[1]

[그림 1: 이사서비스 피해구제 신청 추이 — 가로축 2023·2024·2025년, 세로축 신청 건수, 막대 값 603·785·961건[1]. 제목 아래 “전체 이사서비스 피해구제 신청”을 명시하고, “시장 규모·전체 이용자의 피해율을 뜻하지 않음” 각주 표시]

소규모 이사 피해 유형 중 추가비용 요구는 **70건·24.9%**[1], 이행 거부·계약불이행은 **39건·13.9%**[1]였다. 이는 피해구제 사건 **241건**[1]에서 유형을 중복 집계한 **281건**[1]을 분모로 한다. 가장 많은 유형은 파손·분실 **47.7%**[1]다.

**추정: 초기 서비스는 계약 전에 질문하고 기록할 수 있는 ‘포함 범위와 작업조건의 불확실성’에 집중한다.** 소비자원 역시 방문견적, 허가·보험 확인, 상세한 계약사항 기재를 권고한다.[19]

[표 2: 견적의 빈칸이 문제가 되는 과정 — 열 구성: 시점 / 사용자가 확인하기 어려운 것 / 필요한 도움]

| 시점 | 사용자가 확인하기 어려운 것 | 필요한 도움 |
|---|---|---|
| 견적을 받을 때 | 내 짐과 계단·주차·분해설치 조건이 반영됐는가 | 조건과 견적의 항목별 대조 |
| 계약금을 보내기 전 | “기본 포함”, “현장 협의”가 어디까지를 뜻하는가 | 업체에 보낼 구체적인 확인 질문 |
| 이삿날 | 사전에 무엇을 설명하고 어떤 답을 받았는가 | 견적 원문과 답변을 연결한 확인 기록 |

**관악구에서 시작할 이유**

국무조정실은 관악구의 청년인구 비율을 2024년 기준 **41.4%·전국 1위**[5]로 소개했다. 현재 연도의 순위는 **unknown**이다.  
**추정: 청년의 소규모 이사 준비 과정을 가까이서 검증할 초기 지역으로 관악구를 설정한다.**

서울시는 청년 중개보수·이사비를 실제 지출 범위에서 최대 **40만원**[22] 지원하는 사업을 운영했다. 해당 사업의 2026년 상반기 신청자 중 **89.4%**[22]는 1인가구, **72%**[22]는 원룸 거주자였다. 이는 지원사업 신청자 특성이며 전체 청년의 주거 분포는 아니다.

**계획:** 청년 주거·이사 지원 안내에 계약 전 점검 도구를 함께 제공하는 협력 가능성을 검토한다. 비용 지원과 계약조건 확인을 연결하는 구상이며, 기관 제휴는 아직 체결되지 않았다.

*현재 국내 이사서비스의 연간 시장 매출 규모는 **unknown**이다. 초기 시장은 ‘관악구에서 소규모 이사를 준비하며 견적을 확인하는 청년’이라는 구체적인 이용 상황으로 정의한다.*

## p.3 이 사람의 이 순간 — 업체 선택 전부터 송금 직전까지

**사용자는 견적을 받는 데서 끝나지 않고, 자기 조건에 대한 답을 받은 뒤 선택해야 합니다.**

**가상 사용자:** 관악구에서 자취방을 옮기는 대학생. 이사 경험이 적고, 아직 업체를 정하지 않았다. 아래 문구는 사용 흐름을 설명하기 위한 가상 예시이며 실제 인터뷰가 아니다.

> **사용자 조건:** “지금 집은 엘리베이터가 없어요. 침대도 옮겨야 해요.”  
> **견적 문구:** “기본 작업 포함. 현장 상황에 따라 협의.”

사용자에게 필요한 것은 이 문구를 요약하는 답만이 아니다. **계단 운반과 침대 작업이 포함됐는지, 별도 비용이 생기는 조건은 무엇인지** 확인할 수 있어야 한다.

[그림 2: 한 사용자의 이사 준비 여정 — 조건 정리 → 견적 받기 → 문의·비교 → 계약금 송금 → 이삿날의 가로 흐름. 조건 정리부터 문의·비교까지를 서비스 개입 구간으로 강조하고, 송금 직전에 “미확인 항목 다시 확인” 표시. 업체의 모호한 답변은 문의 단계로 되돌아가는 화살표로 표현]

- **조건 정리:** 한 문장으로 상황을 입력하고, 해석된 출발·도착 조건과 짐 항목을 직접 확인한다.
- **견적 받기:** 받은 견적을 넣는다. 업체를 아직 찾지 못했다면, 공공 허가 목록에서 후보를 탐색하는 기능을 제공할 계획이다.
- **문의·비교:** 업체마다 같은 항목을 확인하고, 답변이 충분한지 살핀다.
- **송금 전:** 남아 있는 미확인 항목과 답변 원문을 보고 사용자가 계약 여부를 결정한다.
- **이삿날:** 계약 전에 확인한 조건을 다시 살핀다. 별도 당일 대응 기능은 후속 범위다.

**질문이 생기면 다음 행동이 달라진다**

견적의 “기본 작업 포함”은 다음 확인 문구로 이어진다.

> “출발지에 엘리베이터가 없습니다. 계단 운반과 침대 분해·조립이 견적에 포함되나요? 별도라면 발생 조건과 금액을 견적서에 적어 주세요.”

업체가 “당일 보고 결정합니다”라고 답하면 **미확인 상태를 유지**한다. 구체적인 작업·비용 조건을 답하면 해당 항목과 연결해 사용자가 원문을 검토한다. 답변이 있다는 이유만으로 포함 여부를 확정하지 않는다.

**추정: 이용자는 이사 준비 청년이고, 유료 도입 후보는 지자체·청년지원기관·대학이다.** 사용자의 계약 전 확인을 무료로 돕고, 기관에는 이용권과 운영 기능을 제공하는 모델을 검증한다.

## p.4 해결 방식과 사용 흐름 — 조건에서 질문, 답변에서 비교로

**한 문장으로 시작해, 견적의 미확인 항목을 질문하고 답변을 비교하는 흐름을 제공합니다.**

아래 핵심 흐름은 **D006 구현 기록 기준으로 동작하는 웹 프로토타입**이다. 새로 보강하는 기능은 계획으로 구분한다.[D006]

**① 내 이사 조건 정리 — 구현됨**  
자연어로 입력한 조건을 읽어 맞춤 화면을 구성한다. 사용자는 출발·도착지의 작업조건과 짐 항목을 확인하고 수정한다. 확인되지 않은 차량·인원은 업체에 물어볼 항목으로 남긴다.

**② 받은 견적 읽고 대조 — 구현됨**  
견적의 금액·작업조건·포함 문구를 추출하고 사용자 조건과 대조한다. 결과는 **명시됨 / 포함 여부 미확인 / 조건 모호 / 판독 불가**로 구분한다. 사용자가 카드에서 근거 원문으로 이동해 확인할 수 있다.

**③ 업체별 문의와 답변 점검 — 구현됨**  
미확인 항목을 업체에 보낼 문구로 만들어 복사한다. 사용자가 받은 답변을 입력하면 해당 후보의 항목에 연결해 점검한다. 문의 발송과 계약 결정은 사용자가 수행한다.

**④ 같은 항목으로 후보 비교 — 구현됨**  
후보별로 작업조건·포함 범위·미확인 항목을 같은 행에 놓는다. 비교표는 입력 순서로 제시하며, 자동 순위나 추천 점수를 부여하지 않는다.

**⑤ 계약 전 마지막 점검 — 규칙 점검 구현됨 / 계약서 AI 읽기 계획**  
계약 관련 항목을 규칙으로 확인한다. 계약서 자체를 AI로 읽어 반영하는 기능은 후속 개발 범위다.

[그림 3: 조건에서 계약 전 확인까지 — ① 조건 입력·맞춤 화면 → ② 견적 대조·원문 확인 → ③ 문의·답변 → ④ 후보 비교 → ⑤ 계약 점검 흐름도. ①~④에는 현재 웹의 실제 화면 캡처를 배치하고, ⑤에는 “규칙 점검 구현됨 / 계약서 AI 읽기 계획” 배지 표시. 가상 견적은 실존 업체명과 연결하지 않음]

**계획: 업체를 찾는 단계도 연결한다**

현재는 관악구 공공 허가 목록과 입력 업체명을 대조하는 기능이 구현돼 있다.[D006] 이를 **견적 받을 후보를 찾아보는 기능**으로 보강한다. 목록의 동일 상호 기록만으로 동일 업체나 현재 허가 상태를 확정하지 않으며, 허가증 사본 확인으로 연결한다. 보험 가입도 별도로 확인해야 한다.[19]

**계획: 작업 결과를 근거 장부로 묶는다**

현재 제공하는 카드별 원문 추적을 바탕으로, 어떤 입력을 읽고 어떤 근거로 항목을 표시했는지 한곳에서 살펴보는 근거 장부를 보강한다. 화면의 작업 장면은 실제 처리 상태와 결과를 설명하는 용도로 사용한다.

**다음 쪽에서는 이 흐름에서 AI가 읽는 정보와, 사용자 확인·규칙 검증을 거쳐 결과가 반영되는 방식을 설명한다.**

## p.6 왜 다른가 — 받은 견적을 확인 가능한 선택으로

**차별화의 초점은 외부 견적의 모호한 문구를 질문·답변·원문 근거까지 이어 주는 데 있습니다.**

**추정: 이사 지킴이가 검증할 차별화 가설은 ‘사용자가 여러 자료를 오가며 하던 계약 전 확인을 하나의 흐름으로 줄일 수 있다’는 것이다.**

[표 4: 계약 전 확인 작업의 연결 방식 — 열 구성: 사용자 과업 / 자료를 따로 확인하는 방식 / 이사 지킴이의 연결 방식. 특정 경쟁 제품의 기능 부재나 열위를 뜻하지 않는 작업 방식 비교임을 각주로 표시]

| 사용자 과업 | 자료를 따로 확인하는 방식 | 이사 지킴이의 연결 방식 |
|---|---|---|
| 조건 정리 | 메모와 상담 내용을 보고 조건을 다시 설명 | 확인한 조건을 견적 대조와 문의에 이어 사용 |
| 견적 읽기 | 문서마다 작업 범위와 표현을 직접 해석 | 항목별 표시와 해당 원문을 함께 확인 |
| 빈칸 확인 | 무엇을 질문할지 스스로 작성 | 미확인 항목에서 문의 문구로 연결 |
| 업체 비교 | 총액과 개별 대화를 번갈아 확인 | 공통 항목별 답변·미확인 상태를 나란히 확인 |
| 계약 점검 | 견적·답변·계약 관련 정보를 각각 확인 | 규칙 점검 제공, 계약서 AI 읽기는 후속 계획 |

**유사 서비스와 맞닿는 부분도 분명하다**

확인한 공개 자료에서 짐싸는 견적·계약·결제·분쟁 처리 지원을 안내한다.[11] 미소는 방문 조사와 견적 비교, 표준 견적·영상 증빙을 소개했다.[17] Yembo는 AI 조사 정보를 인벤토리·견적·클레임 기록으로 연결하는 기업용 제품을 제공한다.[18]

따라서 **견적 검토·질문 안내·증빙 확보 자체를 최초 기능으로 주장하지 않는다.** 이사 지킴이는 소비자가 이미 받은 외부 견적을 자신의 작업조건과 대조하고, 업체의 답변이 충분한지 확인하며, 판단의 근거를 다시 찾을 수 있게 하는 흐름에 집중한다. 경쟁사의 동일한 연결 기능 제공 여부는 확인한 공개 자료만으로는 **unknown**이다.

**신뢰를 위한 제품 원칙**

- **미확인은 그대로 표시:** “현장 협의”처럼 확정되지 않은 답변을 포함·해결로 바꾸지 않는다.
- **질문의 근거를 제공:** 견적 발췌와 사용자 조건을 함께 보여 주고, 공공 권고를 참고 안내로 연결한다.[19]
- **결제와 비교 결과를 분리:** 업체의 광고·제휴 대가로 누락 표시나 비교 순서를 바꾸지 않는 운영 원칙을 제안한다.
- **판단 범위를 명확히 설정:** 가격 적정성·위법 여부·배상액을 자동 판정하지 않는다. 추가비용은 조건 변경과 사전 고지 등 구체적인 사정을 확인해야 한다.[20]

**추정: 기대 가치는 질문 작성 부담을 줄이고, 남아 있는 불확실성을 사용자가 알아보게 하는 것이다.** 실제 효과는 마지막 쪽의 비교 실험과 사용 검증으로 평가한다.

## p.8 가치 검증과 지속 가능성 — 무료 점검에서 기관 도입으로

**소비자의 확인 행동이 달라지는지 먼저 측정하고, 그 가치를 기관이 구매할 수 있는지 검증합니다.**

**추정: 효과 검증 가설**

현재 웹의 동작은 확인했지만, 실제 피해 감소·이용 의사·기관 구매 의사는 아직 검증하지 않았다. 성과 평가는 일반 안내문을 보고 확인하는 경우와 서비스를 사용하는 경우를 비교하되, 사례 난이도와 순서 효과를 통제하도록 설계한다.

*계획: 평가 기준과 통과 목표를 실험 전에 정하고 결과를 공개한다. 실제 추가요금·피해 감소는 이사 이후 추적 자료를 확보한 뒤 별도로 판단한다.*

**추정: 우선 검증할 사업모델 — 소비자 무료 + 기관 유료**

- **소비자:** 조건 정리, 견적 점검, 문의 문구, 답변 비교를 무료로 이용한다.
- **B2G 후보:** 지자체·청년지원기관에 대상자 이용권, 안내 연계, 개인정보를 최소화한 이용 집계 기능을 제공한다.
- **B2B 후보:** 대학·생활협동조합에는 이사 준비 지원 패키지, 주거 플랫폼에는 점검 기능 연동을 제안한다.
- **후속 후보:** 이사업체에는 상세 견적 작성·합의 기록 관리 도구의 수요를 검증한다. 비용을 내는 업체에도 동일한 점검 기준을 적용한다.

서울시는 민간 AI 전세사기 위험분석 서비스 ‘내집스캔’을 무료 쿠폰으로 지원한 사례가 있다.[23] 이는 공공기관을 통한 이용 지원의 참고 사례이며, 이사 지킴이의 계약 수주나 수익성을 입증하는 자료는 아니다.

**추정: 수익성과 중립성의 검증 기준**

기관형 매출은 **계약기관 수 × 기관당 계약금액**, 연동형 매출은 **기본료 + 유료 처리 건수 × 건당 요금**으로 검토한다. 여기서 추론·문서처리·운영·고객지원 비용을 차감해 지속 가능성을 판단한다. 실제 가격·처리 원가·도입률·갱신률은 모두 **unknown**이다.

업체 광고·계약 성사 수수료는 초기 우선 수익원에서 제외하는 안을 제안한다. 향후 제휴를 도입하더라도 관계를 표시하고, 점검 기준·미확인 표시·비교 순서를 대가와 연결하지 않는다. 이사비 지원금에서 수수료를 받는 구조도 전제하지 않는다.

**계획: 확장은 검증 결과에 따라 진행한다**

관악구 청년 대상 사용 검증 → 기관 도입 의사·비용 검증 → 다른 지역의 출처·이용 조건을 확인한 업체 목록 확장 → 주거 플랫폼 연동 순으로 진행한다. 기관에는 실제 주거 사진·견적 원문을 기본 제공하지 않는 운영안을 설계한다.

남은 핵심 과제는 **한국어 견적·답변 점검의 정확도, 기관의 구매 의사, 운영 원가, 지역별 데이터 최신성**이다. 현재 구현한 흐름을 토대로 이 항목을 검증하면서 범위를 넓힌다.
