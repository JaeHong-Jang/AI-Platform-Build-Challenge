# B012 에이전트 중심 재설계

## 사용자 요구 (2026-10-25 00:50)
1. "문제는 정말 정확한 거야?" — 문제 정의를 출처에 맞게 바로잡는다.
2. "AI Agent가 명확히 해결하는 데 사용되어야" — 지금은 문제를 푸는 판단(빈칸 찾기·질문·계약 점검)이 모두 코드이고 AI는 읽기·답변 분류만 한다.
3. 범위 B: **웹을 먼저 에이전트 중심으로 바꾸고 동작을 확인한 뒤** 기획서(hwpx)를 고친다. 오케스트라 구조로 진행.

## Opus 진단 (조사 전 가설 — 실무팀이 검증)
- 수치(603→785→961, 241건 중 20~30대 65.1%, 추가비용 70/281=24.9%)는 원문과 일치(10/23 대조).
- 원인 서술이 출처와 어긋남: 소비자원은 원인을 **비대면 계약(방문 견적 없이 구두·온라인 입력)**, 사유를 **짐 양·건물 구조로 화물차·인력·사다리차 추가**, 결과를 **거부 시 계약불이행(13.9%)**으로 설명. 기획서는 '견적 문구가 모호하다'에 무게.
- "원룸 짐 일체"·"현장 상황에 따라 추가 비용"은 팀 합성 평가셋 문장인데 2번 요약에서 실제 문구처럼 읽힘.
- "청년은 질문을 떠올리지 못한다"는 근거 없음. 피해 1위 파손·분실(47.7%) 미언급.

## 설계 방향 (Opus 초안)
- **점검 에이전트(AI, 도구 사용)**가 사례를 맡는다: 목표 "계약금 전에 당일 추가비용 사유(짐 양·건물 구조·작업 조건)를 업체의 글로 확인받는다".
  - 도구: 사례 보기(내 조건·짐·검증된 견적 값·견적 문장) · 견적 문장 찾기 · 기준선 규칙 결과 · 점검 결과 제출(코드 검증기가 수락/거절+이유).
  - 하는 판단: 내 조건 조합에서 추가비용 지점 추론 → 견적이 그것을 덮는지 판정(근거 문장) → 업체에 보낼 맞춤 질문.
- **답변 점검 에이전트(AI)**: 기존 + 조건부·미답 항목에 되물을 질문.
- 코드는 도구와 안전장치로: 원문 대조(잠금), 규칙 기준선(평가 기준·모델 실패 시 대체), 계약금 비율, 허가 목록. 사람 승인 유지.
- 안전 병합: 에이전트가 '명시됨'을 주장하면 원문 문장·조건어 검사를 통과해야 한다. 새로 찾은 위험은 카드로 추가.
- 모델: 시제품은 로컬 Ollama, 배포 Claude Sonnet 5.5.

## 성공 기준
- 웹: 견적을 넣으면 점검 에이전트가 실제로 도구를 호출하고(작업 기록에 보임), 그 결과가 카드·장면·질문에 반영된다. 모델이 실패하면 규칙 기준선으로 돌아간다. 시험 통과, 타입 검사 통과, 실제 브라우저 확인.
- 기획서: 문제 서술의 모든 주장이 출처와 일치(실무팀 검증), AI 에이전트가 문제를 푸는 주체로 읽힌다.
